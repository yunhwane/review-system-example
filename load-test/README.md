# 부하 테스트

## 설치

```bash
brew install k6
```

## 실행

```bash
# 리뷰 목록 조회 (주력 시나리오, 약 6분)
k6 run load-test/k6/browse.js

# 평점 요약 API (집계가 무거운 시나리오, 약 3분)
k6 run load-test/k6/summary.js

# 결과를 파일로 남기기
mkdir -p load-test/results
k6 run --out json=load-test/results/v1-browse.json load-test/k6/browse.js
```

## VU 를 현실의 동시 사용자로 환산하기

**k6 의 VU 수는 동시 사용자 수가 아닙니다.** 이걸 혼동하면 결론이 통째로 틀어집니다.

```
현실의 동시 사용자 = VU × (현실 think time / 테스트 think time)
```

이 레포의 기본값 기준:

| 테스트 VU | 스크립트 think time | 현실 think time | 환산 동시 사용자 |
| --- | --- | --- | --- |
| 50 | 1초 | 30초 | 1,500명 |
| 100 | 1초 | 30초 | 3,000명 |
| 200 | 1초 | 30초 | 6,000명 |
| 400 | 1초 | 30초 | 12,000명 |

즉 목표인 **동시 사용자 10만 명은 VU 약 3,300에 해당**합니다.
노트북 한 대로는 그만큼의 VU를 만들기 어렵기 때문에, 이 레포에서는
**"한 대가 감당하는 RPS"를 측정한 뒤 [용량 산정 문서](../docs/00-capacity-planning.md)의 계산으로 필요한 대수를 역산**합니다.
이게 실무에서 하는 방식이기도 합니다 — 10만 명분 부하를 실제로 만들어 보는 회사는 드뭅니다.

## 주의사항

**부하를 주는 쪽(k6)과 받는 쪽(앱)이 같은 노트북입니다.**

- k6 자체가 CPU를 먹기 때문에, 앱의 한계보다 낮은 수치가 나올 수 있습니다
- k6 실행 중 `top`으로 k6 프로세스의 CPU를 확인하세요. k6가 코어를 다 쓰고 있으면 측정값을 신뢰할 수 없습니다
- macOS는 기본 파일 디스크립터 한도가 낮습니다. VU를 크게 올릴 거면 `ulimit -n 65536`
- 절대값보다 **변경 전후의 비율**을 보세요. 같은 노트북에서 잰 상대 비교는 신뢰할 수 있습니다

## 측정 순서

1. 앱을 띄우고 **워밍업**: JIT 컴파일과 커넥션 풀 준비 때문에 첫 30초는 느립니다. 본 측정 전에 한 번 가볍게 돌리세요
2. Grafana(http://localhost:3000)를 열어 둔 채로 테스트를 실행합니다
3. k6 요약 출력과 Grafana 패널을 **같은 시간대로** 대조합니다
4. `docs/experiments/`에 기록합니다

숫자만 적고 지표 모양을 안 보면 "느리다"는 것만 알고 "왜 느린지"는 모른 채 끝납니다.
