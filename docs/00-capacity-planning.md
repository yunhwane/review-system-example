# 용량 산정 (Capacity Planning)

> 이 레포에서 제일 먼저 읽어야 할 문서입니다.
> 아키텍처 설계의 출발점은 프레임워크 선택이 아니라 **숫자를 세는 일**입니다.

## 1. "동시 사용자 10만 명"은 무슨 뜻인가

이 말은 그 자체로는 아무 의미가 없습니다. 최소 세 가지로 해석되고, 각각 요구되는 서버가 100배 차이 납니다.

| 해석 | 의미 | 필요한 처리량 |
| --- | --- | --- |
| A. 동시 접속 사용자 | 10만 명이 사이트를 "보고 있다" | 대부분 화면만 보고 있음 → 실제 요청은 훨씬 적음 |
| B. 동시 요청 | 같은 순간 10만 개 요청이 서버 안에 있다 | 극단적. 초대형 서비스 수준 |
| C. RPS 10만 | 초당 10만 요청 | 국내 최상위 트래픽 |

**대부분의 "동시 사용자 10만"은 A입니다.** 이 레포도 A로 잡습니다.
설계를 시작하기 전에 요구사항을 이 셋 중 하나로 반드시 좁혀야 합니다. 이걸 안 하고 시작하면
"일단 MSA로 가죠" 같은 근거 없는 결론이 나옵니다.

## 2. 해석 A → RPS 환산

사용자는 요청을 쉬지 않고 보내지 않습니다. 화면을 읽는 시간(think time)이 있습니다.

```
RPS = 동시 사용자 수 / 평균 요청 간격(think time)
```

리뷰 목록을 읽고 스크롤하는 사용자의 요청 간격을 30초로 잡으면:

```
100,000명 / 30초 ≈ 3,333 RPS
```

여기에 피크 배수를 곱합니다. 광고·푸시·타임세일이 걸리면 평균의 2~3배가 몰립니다.

```
목표: 평상시 3,333 RPS / 피크 10,000 RPS
```

**동시 사용자 10만이 RPS 10만이 아니라 3,300입니다. 30배 차이입니다.**
이 한 줄을 계산했느냐 아니냐가 설계 전체를 가릅니다.

think time을 5초로 잡으면 20,000 RPS가 됩니다. 그래서 think time은 **추측이 아니라 측정해야 하는 값**이고,
없으면 가정을 명시적으로 문서에 적어야 합니다. (이 문서: 30초로 가정)

## 3. Little's Law — 서버 안에 몇 개의 요청이 동시에 살아 있는가

```
L = λ × W
L: 시스템 안에 동시에 존재하는 요청 수
λ: 도착률 (RPS)
W: 평균 응답 시간
```

목표 3,333 RPS에서 응답 시간에 따라:

| 평균 응답 시간 W | 동시 처리 요청 수 L |
| --- | --- |
| 10ms | 33 |
| 50ms | 167 |
| 200ms | 667 |
| 1s | 3,333 |

**응답이 느려지면 필요한 동시 처리 능력이 비례해서 커집니다.**
그래서 튜닝으로 응답 시간을 1/4로 줄이면 서버를 4배 덜 쓰는 것과 같은 효과가 납니다.
스케일아웃보다 최적화를 먼저 하는 이유가 이것입니다.

역방향으로도 씁니다. 톰캣 스레드가 200개고 응답이 50ms면 이론상 한 대가 감당하는 상한은:

```
λ = L / W = 200 / 0.05s = 4,000 RPS
```

## 4. v1은 어디서 무너질 것인가 (측정 전 예측)

예측을 먼저 적고 나중에 실측과 비교하는 것이 학습의 핵심입니다. 틀려도 됩니다. **틀린 지점이 배울 지점입니다.**

v1의 기본 설정:

- 톰캣 스레드: 200 (Spring Boot 기본)
- HikariCP 커넥션 풀: **10** (Spring Boot 기본)
- `product_id` 인덱스: **없음** (일부러)
- 캐시: 없음
- 리뷰 목록 조회 시 상품명 접근 → **N+1 쿼리**

리뷰 10만 건 풀스캔에 40ms가 걸린다고 가정하면, DB 커넥션이 진짜 병목입니다:

```
λ = 커넥션 수 / DB 점유 시간 = 10 / 0.04s = 250 RPS
```

**예측: v1은 250 RPS 부근에서 한계. 목표(3,333)의 약 1/13.**
그 이상 부하를 주면 커넥션 풀 대기가 쌓여서 응답 시간이 선형이 아니라 **수직으로** 치솟습니다
(대기 큐가 생기는 순간 지연은 폭발합니다). 이때 CPU 사용률은 오히려 낮게 나옵니다 —
**"CPU가 놀고 있는데 느리다"는 전형적인 커넥션 풀 고갈 신호입니다.**

이걸 Grafana에서 확인할 지표:

| 지표 | 병목일 때의 모양 |
| --- | --- |
| `hikaricp_connections_pending` | 0에서 급격히 상승 |
| `hikaricp_connections_active` | 풀 크기(10)에 딱 붙어서 평평 |
| `http_server_requests_seconds` p95 | 수직 상승 |
| 프로세스 CPU | 의외로 낮음 (40~60%) |

## 5. 데이터 크기 산정 — 10만 건은 사실 작다

리뷰 1건의 크기를 세어 봅니다.

| 컬럼 | 크기 |
| --- | --- |
| id (bigint) | 8 B |
| product_id (bigint) | 8 B |
| author (varchar 50) | ~30 B |
| rating (smallint) | 2 B |
| content (text) | ~500 B |
| helpful_count (int) | 4 B |
| created_at (timestamptz) | 8 B |
| 행 오버헤드 (Postgres ~24B + 정렬) | ~40 B |
| **합계** | **약 600 B** |

```
100,000건 × 600B ≈ 60 MB
인덱스(product_id, created_at) 포함해도 100 MB 미만
```

**즉 데이터 전체가 DB 서버 메모리에 통째로 들어갑니다.** 디스크 I/O는 사실상 병목이 아닙니다.

이게 이 시나리오의 가장 중요한 통찰입니다:

> **리뷰 10만 건에서 병목은 "데이터 양"이 아니라 "동시성"이다.**

그래서 v2~v4의 최적화는 전부 "한 요청을 얼마나 빨리 끝내서 자원을 빨리 반납하느냐"에 관한 것이고,
샤딩·파티셔닝 같은 데이터 분할 기법은 이 규모에서 **필요 없습니다**.
(그걸 배우고 싶다면 시드 데이터를 1,000만 건으로 늘리는 별도 축으로 실험하세요. 로드맵 부록 참고.)

## 6. 네트워크 대역폭 — 자주 빠뜨리는 계산

리뷰 20건짜리 응답 1개가 약 20 KB라면:

```
3,333 RPS × 20 KB = 66 MB/s ≈ 533 Mbps
피크 10,000 RPS × 20 KB = 200 MB/s ≈ 1.6 Gbps
```

**피크에서 1Gbps NIC 한 장을 넘깁니다.** CPU와 DB가 멀쩡해도 여기서 막힙니다.
대응은 코드가 아니라 설계입니다 — 응답 필드 줄이기, gzip 압축, 페이지 크기 축소, CDN.
`size=100`으로 페이징을 열어 두면 이 숫자가 5배가 됩니다. **페이지 크기 상한은 성능 파라미터입니다.**

## 7. 필요한 서버 대수 (v5 스케일아웃 단계에서 검증)

v2~v4 최적화 후 한 대가 1,000 RPS를 안정적으로 처리한다고 가정하면:

```
평상시 3,333 RPS ÷ 1,000 = 4대
피크 10,000 RPS ÷ 1,000 = 10대
+ 장애 여유(N+1) 및 배포 중 여유 → 12대
```

여기서 반드시 같이 물어야 하는 질문:

- 앱을 12대로 늘리면 **DB 커넥션은 12 × 풀 크기**가 됩니다. Postgres `max_connections` 기본값은 100입니다. → 먼저 터지는 건 DB입니다.
- 그래서 스케일아웃에는 커넥션 풀 재산정 또는 PgBouncer 같은 커넥션 풀러가 따라옵니다.
- 이게 **"스케일아웃은 공짜가 아니다"**의 구체적인 사례입니다. v5에서 직접 재현합니다.

## 8. 스케일업 vs 스케일아웃, 무엇을 먼저?

| | 스케일업 (서버 사양 ↑) | 스케일아웃 (대수 ↑) |
| --- | --- | --- |
| 장점 | 코드 변경 없음, 즉시 적용 | 이론상 무한, 장애 격리 |
| 단점 | 상한이 있고 비용이 초선형, SPOF 유지 | 무상태 설계 필요, DB가 새 병목 |
| 적합 | DB(쓰기), 캐시 서버 | 웹/앱 계층 |

실무 순서는 대체로 이렇습니다:

```
1. 측정한다 (안 하면 나머지가 전부 추측)
2. 코드/쿼리를 고친다 (가장 싸다 — 인덱스 하나가 서버 10대를 아낀다)
3. 캐시를 붙인다
4. 스케일업 (가장 빠른 임시 처방)
5. 스케일아웃 (구조 변경을 동반)
6. 아키텍처를 쪼갠다 (읽기/쓰기 분리, 비동기화, 서비스 분리)
```

**대부분의 "MSA로 가야 하나요?"는 2번에서 끝날 문제입니다.**
이 레포의 v1→v2 실험에서 그걸 숫자로 확인하게 됩니다.
