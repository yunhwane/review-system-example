# 부하 테스트 — 측정 도구를 먼저 의심하라

측정값이 시스템의 한계인지 **부하 도구의 한계**인지 구분하지 못하면, 그 뒤의 모든 결론이 무너집니다.
이 문서는 그걸 구분하는 방법입니다.

`docs/02-monitoring.md` 4절 진단표의 마지막 줄 — "**RPS가 안 오름 + 모든 자원이 한가함 = 부하 도구가 병목**" —
을 실제로 판별하는 절차라고 보면 됩니다.

## 0. 이 문서가 생긴 이유

v2 측정 과정에서 **같은 실수를 세 번** 했습니다.

| 실험 | 측정된 RPS | 실제로는 |
| --- | --- | --- |
| v2-1 (인덱스) | 399.9 | 시스템 한계가 아니라 **VU 400 ÷ think 1초의 산술 상한** |
| v2-2 (부하 상향) | 1,404 | 이번엔 진짜 한계였지만, **확인하는 데 별도 추론이 필요**했다 |
| v2-3 (커서) | 1,318 | 커넥션 풀 한계. 도구는 여유 있었지만 **그걸 증명하기 어려웠다** |

매번 "부하가 모자란 건가, 시스템이 한계인가"를 `pending`·`active`·CPU 를 보고 **추론**해야 했습니다.
추론이 필요하다는 것 자체가 도구 선택이 잘못됐다는 신호입니다.

## 1. 닫힌 모델 vs 열린 모델 ★

부하 테스트에는 두 가지 모델이 있고, **둘은 다른 현실을 흉내 냅니다.**

```
닫힌 모델 (closed) — k6 의 ramping-vus
  VU 는 응답을 받아야 다음 요청을 보낸다
  RPS = VU ÷ (think time + 응답시간)
  → 시스템이 느려지면 부하가 자동으로 줄어든다
  → 시스템이 스스로를 보호한다

열린 모델 (open) — k6 의 ramping-arrival-rate
  응답과 무관하게 초당 N 건이 계속 도착한다
  RPS = 지정한 값 (시스템이 못 따라가면 큐가 쌓인다)
  → 시스템이 느려져도 부하는 안 줄어든다
```

### 같은 시스템, 14배 차이

2026-08-16 측정에서 같은 코드·같은 장비로:

| 모델 | 부하 | p95 |
| --- | --- | --- |
| 닫힌 (`ramping-vus`, VU 400 / think 0.2s) | 1,341 RPS | **160 ms** |
| 열린 (`ramping-arrival-rate`, 목표 3,200 RPS) | 1,094 RPS | **2,300 ms** |

**닫힌 모델이 시스템을 봐주고 있었습니다.**

### 어느 쪽을 써야 하나

**공개 웹 트래픽은 열린 모델입니다.** 사용자는 서버가 느려졌다고 얌전히 기다려주지 않습니다.
새 사용자가 계속 들어오고, 느려진 만큼 새로고침까지 눌러서 오히려 **부하가 늘어납니다.**

닫힌 모델이 맞는 경우는 **고정된 사용자 집단이 순차적으로 일하는 시스템**입니다.
사내 도구, 배치 워커, 커넥션 풀 뒤의 컨슈머 같은 것들이죠.

> **리뷰 조회 API 는 공개 트래픽입니다. 열린 모델이 맞습니다.**

### 열린 모델의 결정적 장점: `dropped_iterations`

닫힌 모델은 "요구한 만큼 못 냈다"를 **말해주지 않습니다.** VU 가 알아서 느려질 뿐입니다.
열린 모델은 초당 N 건을 보내야 하는데 못 보내면 그 횟수를 그대로 알려줍니다.

```
dropped_iterations.......: 51,826  506.865462/s
```

**"요구 대비 얼마를 못 냈는가"가 지표 하나로 나옵니다.** 추론이 사라집니다.

## 2. 보정(calibration) — 장비의 절대 상한을 먼저 잰다

시스템을 재기 전에 **측정 장비 자체가 얼마까지 낼 수 있는지**를 먼저 재야 합니다.

DB 를 건드리지 않는 엔드포인트를 열린 모델로 때립니다.

```js
// load-test/k6/calibrate.js 로 만들어 두면 좋다
export const options = {
  discardResponseBodies: true,
  scenarios: {
    ceiling: {
      executor: 'ramping-arrival-rate',
      startRate: 500, timeUnit: '1s',
      preAllocatedVUs: 200, maxVUs: 2000,
      stages: [
        { duration: '20s', target: 1000 },
        { duration: '20s', target: 2000 },
        { duration: '20s', target: 4000 },
        { duration: '20s', target: 8000 },
        { duration: '20s', target: 16000 },
      ],
    },
  },
};
export default function () {
  http.get('http://localhost:8080/actuator/info');   // DB 를 안 탄다
}
```

2026-08-16 이 노트북(10코어)의 결과:

```
목표 500 → 16,000 RPS 램프
dropped_iterations = 0        ← 한 번도 못 따라간 적 없음
p95 = 300μs,  vus_max = 200   ← VU 를 더 쓸 필요도 없었음
```

**이 장비의 절대 상한은 최소 16,000 RPS 입니다.**
시스템 측정치가 여기에 근접하면 그 숫자는 믿으면 안 됩니다.

> 장비를 바꾸거나, 앱·DB를 다른 곳으로 옮기거나, k6 버전을 올렸다면 **보정을 다시 하세요.**

## 3. 부하 스크립트의 요청당 비용 ★

보정에서 16,000 RPS 가 나왔는데 실제 측정에서는 1,341 RPS 에서 k6 가 **4.6 코어**를 쓰고 있었습니다.
차이는 전부 **스크립트 안에서** 발생합니다.

### CPU 분해 (2026-08-16, 1,341 RPS 시점)

```
시스템 전체   8.9 코어 (10코어 중 89%)
├─ 앱          2.3 코어   (process_cpu_usage 0.23 × 10)
├─ Postgres    1.65 코어  (docker stats 165%)
├─ 기타        ~0.3 코어  (prometheus, grafana, exporter)
└─ k6         ~4.6 코어   ← 앱과 DB 를 합친 것보다 크다 ★
```

**범인은 `JSON.parse` 입니다.** k6 의 JS 엔진(goja)은 인터프리터라 파싱이 느린데,
매 요청 ~6KB 본문 × 1,341 RPS = **초당 8MB** 를 파싱하고 있었습니다.

### 처방

| 처방 | 효과 |
| --- | --- |
| `discardResponseBodies: true` | 본문을 아예 안 받는다. 가장 큼 |
| `check()` 를 줄인다 | 정규식·파싱 검사는 비싸다 |
| 파싱이 꼭 필요하면 **샘플링** | `if (__ITER % 20 === 0)` 일 때만 파싱 |
| 응답 DTO 축소 | 앱·네트워크·k6 **세 곳 모두** 이득 |

커서 시나리오처럼 응답에서 값을 꺼내야 하는 경우에도, 매번 파싱할 필요는 없습니다.
20회에 1번만 파싱해서 커서를 갱신하고 나머지는 재사용하면 됩니다.

> **부하 도구는 "요청을 만드는 일" 외에 아무 일도 하지 않아야 합니다.**

## 4. 크기 계산

### 열린 모델 (권장)

```
목표 RPS = 예상 천장 × 2                    (여유 2배)
maxVUs   = 목표 RPS × 허용 최악 응답시간 × 1.5

예) 목표 4,000 RPS, 허용 최악 응답 0.3초
    maxVUs = 4,000 × 0.3 × 1.5 = 1,800
```

`maxVUs` 가 모자라면 **시스템이 아니라 VU 부족으로** drop 이 납니다.
2026-08-16 측정이 정확히 그 경우였습니다 (maxVUs 3,000 소진, p95 2.3초).

### 닫힌 모델 (기존 시나리오를 유지할 때)

```
RPS = VU ÷ (think time + 응답시간)
VU  = 목표 RPS × (think time + 예상 응답시간)

예) 목표 2,000 RPS, think 0.2초, 예상 응답 0.01초
    VU = 2,000 × 0.21 = 420
```

그리고 **think time 환산을 반드시 기록**해야 합니다.

```
현실 think time 30초 가정 (docs/00-capacity-planning.md)

think 1초   : VU 1 ≈ 현실 사용자  30명
think 0.2초 : VU 1 ≈ 현실 사용자 150명
```

**이 환산을 잊으면 "VU 400밖에 못 버티네"라는 잘못된 결론을 내립니다.**
열린 모델로 가면 이 계산이 통째로 사라지는 것도 장점입니다 — 기준 시나리오가
"평상시 3,333 RPS"이므로 그 숫자를 목표에 그대로 넣으면 됩니다.

## 4-1. p95 는 두 개다 ★

**서버가 재는 p95 와 사용자가 겪는 p95 는 다른 값입니다.** 이걸 혼용하면 장애를 놓칩니다.

| 출처 | 무엇을 재는가 |
| --- | --- |
| Prometheus `http_server_requests_seconds` | **톰캣 스레드가 요청을 집어든 뒤**부터 응답까지 |
| k6 `http_req_duration` | **클라이언트가 보낸 순간**부터 받을 때까지 |

`http_server_requests` 는 **큐에서 기다린 시간을 재지 않습니다.**
톰캣 스레드가 처리를 시작할 때 타이머가 켜지기 때문입니다.

### 실측 (2026-08-16, 열린 모델 포화 상태)

```
사용자가 겪은 1,627ms
├─ 1,460ms  accept 큐 + 소켓 백로그   ← 서버 지표에 안 잡힘 ★
├─   132ms  HikariCP 커넥션 대기       (pending 189 ÷ 1,428 RPS)
└─     7ms  실제 DB 작업

Grafana ② 패널이 보여준 값: 167ms   ← SLO 200ms 아래, 초록불
```

같은 시각 서버 쪽 그림은 이랬습니다:

```
실패율 0%          5xx 도 타임아웃도 없음
앱 CPU 23%         한가함
Grafana p95 167ms  SLO 통과 — 초록불
```

**대시보드는 전부 정상인데 사용자는 1.6초를 기다렸습니다.**

### 그래서

- **SLO 를 서버 지표로만 걸면 이런 장애를 영원히 못 잡습니다.**
- 두 모델 비교에서도 **서버 지표는 차이를 못 보여줍니다** —
  닫힌 160ms vs 열린 167ms 로 거의 같은데, 클라이언트는 119ms vs 1,627ms 로 14배 벌어졌습니다.
- 실무에서 RUM(Real User Monitoring)이나 로드밸런서 지표를 따로 보는 이유가 이것입니다.
- 이 레포에는 그 층이 없으므로 **k6 의 `http_req_duration` 을 사용자 관점 지연의 유일한 출처**로 씁니다.

**실험 기록에 p95 를 적을 때는 출처를 반드시 명시하세요.**
두 값이 벌어지면 **그 차이가 곧 큐 대기 시간**입니다.

## 5. 측정마다 확인할 체크리스트

```
□ dropped_iterations == 0 ?     아니면 요구를 못 채운 것 (열린 모델)
□ vus < maxVUs ?                닿았으면 VU 부족 or 시스템 붕괴 (p95 로 가른다)
□ 시스템 CPU < 80% ?            넘으면 장비 전체가 한계
□ k6 CPU < 앱 CPU ?             넘으면 측정 도구가 주인공이 된 것
□ http_req_blocked 안 오르나?   커넥션 설정에서 병목
□ 앱 지표가 saturation 을 보이나?  pending / active / 톰캣 busy
□ 서버 p95 와 클라이언트 p95 를 둘 다 적었나?  차이가 곧 큐 대기 시간 (4-1절)
```

`vus` 가 `maxVUs` 에 닿았을 때는 **응답시간으로 원인을 가릅니다.**

```
p95 > 응답시간 예산  → 시스템이 무너져서 VU 가 쌓인 것    (C, 신뢰 가능)
p95 정상            → 그냥 maxVUs 설정이 낮았던 것        (E, 설정 실수)
```

이 구분을 못 하면 **시스템 포화를 "설정 실수" 로 오진**합니다.
열린 모델에서 포화의 전형적인 모양이 정확히 "응답이 늘어지며 VU 가 쌓이는 것" 이기 때문입니다.
`browse-arrival.js` 는 이 판정을 요약에 자동으로 찍습니다.

**마지막 줄이 핵심입니다.** 부하 도구가 한계면 앱 쪽 saturation 지표가 **전부 0** 입니다.
시스템이 한계면 `pending` 이나 `active` 중 하나는 반드시 차 있습니다.

| 상황 | dropped | 앱 pending/active | 시스템 CPU | 판정 |
| --- | --- | --- | --- | --- |
| A | 0 | 0 | 낮음 | 아직 여유. 부하를 더 줘라 |
| B | 0 | **참** | 보통 | **시스템 한계 — 신뢰 가능** |
| C | **>0** | **참** | 보통 | **시스템 한계 — 신뢰 가능** |
| D | **>0** | 0 | **높음** | **부하 도구/장비 한계 — 신뢰 불가** ★ |
| E | >0 | 0 | 낮음 | maxVUs 부족. 설정을 고쳐라 |

## 6. 이 레포의 시나리오 현황

| 파일 | 모델 | 대상 | 상태 |
| --- | --- | --- | --- |
| `browse.js` | 닫힌 (`ramping-vus`) | OFFSET 페이징 | v1~v2-3 계보. **유지** |
| `browse-cursor.js` | 닫힌 | 커서 페이징 | v2-3 에서 추가 |
| `summary.js` | 닫힌 | 요약 API | v3 캐시용 |

**기존 시나리오를 지우면 안 됩니다.** v1~v2-3 측정이 전부 닫힌 모델이라,
비교 계보를 끊으면 지금까지의 숫자가 무의미해집니다.

열린 모델로 넘어갈 때는 **새 파일로 추가**하고, 전환 시점을 실험 문서에 명시하세요.
전환하는 실험에서는 **두 모델을 같은 조건으로 한 번씩 돌려서** 계보를 이어 붙여야 합니다.

## 7. 자주 하는 실수

**① 같은 노트북에서 부하를 준다**

피할 수 없다면 최소한 **CPU 분해를 매번 기록**하세요. k6 가 앱보다 CPU 를 많이 쓰면 그 측정은 의심스럽습니다.

**② 워밍업을 한쪽에만 준다**

v2-3 에서 OFFSET 경로만 워밍업된 상태로 커서와 비교해서, 커서의 첫 계단이 콜드 스타트로 오염됐습니다
(점유 12.7ms vs 다른 구간 6.5ms). **A/B 비교는 두 경로를 모두 데운 뒤에** 하세요.

**③ 저부하에서 잰 값으로 천장을 예측한다**

`한계 RPS = 커넥션 수 ÷ 점유 시간` 은 맞지만, **점유 시간은 상수가 아니라 부하의 함수**입니다.
v2-2 에서 6.2ms → 7.1ms 로 늘어 예측이 13% 빗나갔습니다. 자원이 포화에 가까워질수록 단위 작업이 느려집니다.

**④ `bootRun` 으로 성능을 잰다**

Spring Boot 의 `bootRun` 은 `-XX:TieredStopAtLevel=1` 로 뜹니다. **C2 JIT 이 꺼진 상태**입니다.
기동은 빠르지만 최적화가 덜 됩니다. 비교 측정에는 문제없지만 **절대 수치는 프로덕션보다 비관적**입니다.

**⑤ "훑는 행 수"를 비용의 대리지표로 쓴다**

v2-3 에서 훑는 행을 97% 줄였는데 처리량이 그대로였습니다.
셰어드 버퍼에 있는 인덱스를 훑는 비용은 거의 없고, 실제 비용은 **쿼리 1회당 약 55μs 의 왕복 오버헤드**였습니다.
**행 수와 쿼리 수를 둘 다 보세요.**

## 8. 직접 해 볼 것

1. `calibrate.js` 로 본인 장비의 절대 상한을 재고 실험 문서에 기록하기
2. 같은 시나리오를 `ramping-vus` 와 `ramping-arrival-rate` 로 한 번씩 돌려서 p95 차이를 직접 보기
