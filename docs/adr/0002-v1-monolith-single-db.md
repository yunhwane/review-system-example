# ADR 0002 — v1은 단일 서버 + 단일 DB로 시작하고, 최적화를 넣지 않는다

- 상태: 채택
- 날짜: 2026-08-15

## 배경

목표는 리뷰 10만 건 / 동시 사용자 10만 명이다.
[용량 산정](../00-capacity-planning.md)에 따르면 이 규모의 데이터는 60~100MB로, **DB 메모리에 전부 들어간다.**
즉 데이터 양은 병목이 아니고, 병목은 동시성이다.

이 상태에서 처음부터 캐시·복제본·MSA를 넣으면 두 가지가 망가진다.

1. 각 컴포넌트가 실제로 얼마를 벌어 주는지 측정할 수 없다 (모든 걸 동시에 켰으므로)
2. "필요해서 넣었다"가 아니라 "남들이 쓰길래 넣었다"가 된다 — 정확히 이 레포가 고치려는 문제다

## 결정

v1은 아래 상태로 고정한다.

- 앱 1대, Postgres 1대, 캐시 없음
- `product_id` 인덱스 없음
- 리뷰 목록 조회에 N+1 쿼리 존재
- OFFSET 페이징
- 요약 통계는 요청마다 집계
- HikariCP 풀 크기 = Spring Boot 기본값 10

이건 실수가 아니라 **의도된 초기 조건**이다. 코드 주석에도 그렇게 적혀 있다.

## 대안

**대안 1: 처음부터 인덱스와 캐시를 넣은 "합리적인 v1"**
현실적이지만, 인덱스가 몇 배를 벌어 주는지 체감할 기회가 사라진다.
실무에서 "인덱스 추가"를 제안할 때 근거로 댈 자기 숫자가 안 남는다.

**대안 2: 처음부터 MSA + Kubernetes**
최종 형태를 빨리 볼 수 있지만, 각 조각이 왜 필요한지 모른 채 조립하게 된다.
또한 이 규모(10만 건)에서 MSA는 실제로 **필요 없다.** 필요 없는 걸 정답으로 학습하게 된다.

**대안 3: 인덱스는 넣되 캐시만 뺀다**
절충안이지만, v1의 목적이 "명확하게 무너지는 지점을 보는 것"이라 무너짐이 흐려진다.

## 결과

**얻는 것**

- v1이 몇 RPS에서 무너지는지, 그때 지표가 어떤 모양인지에 대한 자기 데이터
- v2~v6에서 변경 하나하나의 효과를 독립적으로 측정 가능
- "이 규모에 이 기술이 필요한가?"를 숫자로 답하는 습관

**포기하는 것**

- 이 코드는 어떤 의미로도 프로덕션 참고용이 아니다. 그대로 베끼면 안 된다.
- v1 부하 테스트는 낮은 RPS에서 끝나므로 첫 측정이 다소 허무할 수 있다.

## 재검토 조건

리뷰 데이터가 1,000만 건 이상으로 커지면 "데이터 양은 병목이 아니다"라는 이 ADR의 전제가 깨진다.
그 시점에 파티셔닝/아카이빙을 다루는 새 ADR을 쓴다.
