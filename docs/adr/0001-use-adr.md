# ADR 0001 — 아키텍처 결정을 문서로 남긴다

- 상태: 채택
- 날짜: 2026-08-15

## 배경

이 레포의 목적은 동작하는 리뷰 시스템을 만드는 게 아니라 **아키텍처 설계 능력을 기르는 것**이다.
설계 능력은 구조를 만들어 본 경험보다, 선택지를 비교하고 근거를 남긴 경험에서 자란다.
코드만 남기면 6개월 뒤에 "왜 이렇게 했더라"가 남지 않는다.

## 결정

구조를 바꾸는 결정마다 ADR을 한 장씩 쓴다. 형식은 아래 4개 절로 고정한다.

```
# ADR NNNN — 제목
- 상태: 제안 | 채택 | 폐기 | 대체됨(ADR-XXXX)
- 날짜: YYYY-MM-DD

## 배경      무슨 문제가 있었나 (숫자 포함)
## 결정      무엇을 하기로 했나
## 대안      검토했지만 택하지 않은 것과 그 이유
## 결과      무엇이 좋아지고 무엇을 포기했나
```

**"대안" 절이 비어 있는 ADR은 ADR이 아니다.** 비교하지 않은 결정은 결정이 아니라 습관이다.

## 대안

- ADR을 쓰지 않고 README에만 기술: 결정이 누적되지 않고, 나중에 뒤집힌 결정의 이력이 사라진다.
- 커밋 메시지로 대체: 검색이 어렵고 길게 쓰기 어렵다.

## 결과

문서 쓰는 비용이 생긴다. 대신 각 단계에서 무엇을 포기했는지가 남아서,
나중에 요구사항이 바뀌었을 때 "이 결정의 전제가 깨졌다"를 알아챌 수 있다.
