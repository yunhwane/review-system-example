# ADR 0003 — 리뷰 목록을 커서(keyset) 페이징으로 바꾼다

- 상태: 채택
- 날짜: 2026-08-16
- 사후 정정: 2026-08-16 (아래 "사후 검증" 절 — **배경 절의 근거 일부가 틀렸다**)

## 배경

v2-1(인덱스 추가)과 v2-2(부하 상향)를 측정한 결과, **남은 비용이 `count(*)` 로 특정됐다.**

측정 근거는 [v2-2 실험 기록](../experiments/2026-08-16-v2-loadgen-thinktime.md)이다.

**① `count` 가 DB CPU 의 대부분을 태우고 있다**

VU 400 / 1,401 RPS 시점에 초당 1.89M 행을 훑었다. 요청당으로 환산하면 **1,345 행**이고 내역은:

```
목록 (Index Scan)       :    20 행
member N+1              :    20 행
count (Index Only Scan) : ~1,300 행   ← 96%
```

인덱스로 count 는 17배 빨라졌지만(16.5ms → 0.97ms) **훑는 행 수는 전혀 줄지 않았다.**
그 결과 DB CPU 가 처음으로 올라왔다: 25% → 51% → 95% → **140%** (계단별).

**② `count` 는 리뷰 수에 선형으로 나빠진다**

인기 상품은 리뷰가 10,028 건이라 총 개수를 세려고 인덱스 엔트리 1만 개를 매 요청 훑는다.
시드가 지프 분포라 인기 상품이 자주 조회되므로, 평균이 곧 최악에 가깝다.
리뷰가 100만 건이 되면 이 비용이 그대로 100배가 된다.

**③ OFFSET 깊은 페이지는 인덱스로 고쳐지지 않는다 (측정으로 확인)**

`idx_review_product_created` 를 만든 뒤에도 `OFFSET 9000` 은 여전히 `Parallel Seq Scan + Sort` 다.
`enable_seqscan=off` 로 강제해도 10.5ms 로, Seq Scan(15.2ms) 대비 극적인 차이가 없다.

```
OFFSET 9000  →  9,020 건을 읽어야 한다
상품 1의 전체 리뷰 = 10,028 건
즉 그 상품 리뷰의 90% 를 읽는다  →  풀스캔이 이기는 게 맞다
```

**플래너의 판단이 옳다. 이건 튜닝으로 해결할 문제가 아니라 접근 방식의 문제다.**

**④ 현재 병목은 여전히 커넥션 풀이지만, 그 다음이 DB 다**

```
한계 1,404 RPS = 커넥션 10 ÷ 점유 0.0071초
```

풀 크기를 늘리는 건 v4 의 주제다. 그런데 지금 풀을 늘리면 **DB CPU 가 먼저 터진다.**
점유 시간 자체를 줄이는 게 먼저고, 그 안에서 가장 큰 덩어리가 count 다.

## 결정

리뷰 목록 조회를 **커서(keyset) 페이징**으로 바꾼다.

**① 커서는 `(created_at, id)` 복합 튜플로 한다**

```sql
SELECT ... FROM review
WHERE product_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20
```

`created_at` 단독으로는 안 된다. 같은 시각의 행이 둘 이상이면 **경계에서 행이 누락되거나 중복된다.**
현재 시드 데이터는 `created_at` 이 10만 건 모두 유니크하지만, 실서비스에서는 성립하지 않는 가정이다.
`id` 를 타이브레이커로 붙이면 순서가 전순서(total order)가 되어 경계가 항상 명확하다.

**② 커서는 불투명(opaque) 문자열로 인코딩한다**

`base64("{createdAt}|{id}")` 형태로 내보낸다. 클라이언트가 값을 해석하거나 조립하지 못하게 한다.
나중에 정렬 기준을 바꾸면 커서의 내부 구조도 바뀌는데, 투명한 커서를 노출하면 그때 API 가 깨진다.

**③ OFFSET 경로를 남긴다 — 같은 빌드에서 A/B 측정이 가능해야 한다**

```
GET /api/products/{id}/reviews/cursor?cursor=...&size=20   →  커서 페이징 (count 없음)
GET /api/products/{id}/reviews?page=0&size=20              →  기존 OFFSET (count 있음)
```

**별도 경로(`/cursor`)로 나눈다.** 처음에는 같은 경로에서 `cursor` 파라미터 유무로 분기하려 했으나,
그러면 **"커서 페이징의 첫 페이지"와 "OFFSET 페이징의 기본 요청"을 구분할 수 없다** — 둘 다 파라미터가 없다.

이 레포의 작업 방식은 **한 사이클에 한 가지만 바꾸고 전후를 측정하는 것**인데,
OFFSET 경로를 지워 버리면 같은 조건에서 두 방식을 비교할 수 없다.
앱을 재빌드/재기동해서 비교하면 JIT 워밍업과 캐시 상태가 달라져 측정이 오염된다.

**실서비스라면 이건 안티패턴이다** — 두 개의 페이징이 공존하면 유지보수 비용이 든다.
여기서는 **측정 가능성이 우선**이라 의도적으로 남긴다. v3 이후 정리 대상으로 표시해 둔다.

**④ 인덱스는 이번에 바꾸지 않는다**

엄밀히 최적인 인덱스는 `(product_id, created_at DESC, id DESC)` 다.
하지만 인덱스를 같이 바꾸면 **개선의 원인이 커서인지 인덱스인지 구분할 수 없다.**
먼저 기존 `(product_id, created_at DESC)` 로 커서만 도입해 측정하고,
튜플 비교가 인덱스를 제대로 타는지 `EXPLAIN` 으로 확인한 뒤 필요하면 다음 사이클에서 확장한다.

## 대안

**대안 1: OFFSET 유지 + `count` 를 Redis 에 캐싱**

API 계약이 그대로라 가장 변경이 작다. 리뷰 수는 자주 안 바뀌므로 캐시 적중률도 높다.

택하지 않는 이유:
- **깊은 페이지 문제가 그대로 남는다.** count 를 캐싱해도 `OFFSET 9000` 의 Seq Scan + Sort 는 그대로다.
  측정에서 확인된 두 문제 중 하나만 해결한다.
- v3 이 캐시 단계인데 여기서 캐시를 먼저 쓰면 **v3 의 효과를 독립적으로 측정할 수 없다.**
  ADR 0002 가 경계한 "모든 걸 동시에 켜서 각각의 기여를 못 재는" 상황이다.
- 캐시 무효화 정책(리뷰 작성 시 갱신)이라는 새 문제를 들여온다.

**대안 2: 집계 테이블(`review_stats`)에 리뷰 수를 유지한다**

`product_id` 별 카운터를 두고 리뷰 작성 시 증가시킨다. count 가 O(1) 이 된다.

택하지 않는 이유:
- count 는 해결되지만 **깊은 페이지는 여전히 안 고쳐진다.** 대안 1과 같은 한계다.
- 인기 상품 한 행에 쓰기가 몰려 **행 수준 락 경합**이 생긴다. 지프 분포라 이게 실제로 문제가 된다.
- 리뷰 작성과 카운터 갱신의 정합성(트리거 vs 앱 트랜잭션)이라는 새 결정이 필요하다.
- 다만 **요약 API(`/summary`)에는 여전히 유효한 선택지**다. 거기서 다시 검토한다.

**대안 3: 근사 count 를 쓴다**

Postgres `pg_class.reltuples` 나 `EXPLAIN` 의 추정 행 수를 쓰면 스캔 없이 대략적인 수를 얻는다.

택하지 않는 이유:
- `reltuples` 는 **테이블 전체의 추정치**라 `product_id` 별로는 쓸 수 없다. 이 문제에 직접 적용이 안 된다.
- `EXPLAIN` 출력을 파싱하는 방식은 가능하지만, 플래너 통계에 의존해 값이 널뛰고 디버깅이 어렵다.
- 깊은 페이지 문제는 역시 그대로다.

**대안 4: 첫 페이지에서만 count 를 계산한다**

`page=0` 일 때만 총 개수를 주고 이후 페이지에서는 생략한다. 변경이 작다.

택하지 않는 이유:
- 측정상 **요청의 80% 가 첫 페이지**다(`browse.js` 의 분포). 즉 비용의 80% 가 그대로 남는다.
- 응답 형식이 페이지에 따라 달라져서 클라이언트가 지저분해진다.

**대안 5: 아무것도 안 하고 커넥션 풀만 늘린다 (v4 를 앞당김)**

풀을 10 → 50 으로 올리면 산술적으로 천장이 1,404 → 7,000 RPS 가 된다.

택하지 않는 이유:
- **DB CPU 가 이미 140%(1.4 코어) 다.** 풀을 5배로 늘리면 부하가 그대로 DB 로 밀려가 DB 가 먼저 포화된다.
  이건 병목을 옮기는 것이지 없애는 게 아니다.
- 요청당 1,345 행을 훑는 일 자체는 그대로 남는다. 데이터가 늘면 다시 무너진다.
- **분자(풀 크기)를 늘리기 전에 분모(점유 시간)를 줄인다** — v2-2 결론에 적은 순서다.

## 결과

**얻는 것**

- `count` 쿼리 소멸 → 요청당 훑는 행 **1,345 → 약 45 행** (예상)
- 깊은 페이지가 첫 페이지와 같은 비용이 된다. `OFFSET 9000` 의 디스크 정렬이 사라진다
- 리뷰 수가 늘어도 페이지 조회 비용이 **일정하게 유지된다** (선형 → 상수)
- DB CPU 여유가 생겨 v4(풀 크기 튜닝)에서 늘릴 수 있는 폭이 커진다

**포기하는 것**

- **총 개수와 총 페이지 수를 줄 수 없다.** "1,234개의 리뷰", "5,014 페이지" 같은 UI 가 불가능하다
- **N 페이지로 점프할 수 없다.** 이전/다음만 가능하다. 페이지 번호 UI 를 무한 스크롤이나
  "더 보기" 로 바꿔야 한다 — **UI 변경이 따라오는 결정이다**
- 정렬 기준을 바꾸면(예: 도움순) 커서 구조가 달라져 **정렬 기준별로 커서 설계가 따로 필요**하다
- 페이징 경로가 두 개 공존한다 (의도적, 측정용)

**포기하지 않는 것**

`/summary` API 가 총 리뷰 수를 이미 제공한다. "총 몇 건"이 UI 에 꼭 필요하면
목록 API 가 아니라 요약 API 에서 받아 오면 된다. 요약은 v3 에서 캐싱 대상이므로
**총 개수를 얻는 비용이 목록 조회 경로에서 빠져나가 캐시 가능한 경로로 옮겨간다** —
이게 이 결정의 숨은 이득이다.

**검증 방법**

같은 부하 테스트(`k6 run -e THINK_TIME=0.2`)를 커서 경로로 다시 돌려서,
요청당 훑는 행 수와 DB CPU, 한계 RPS 를 v2-2 와 비교한다.
결과는 `docs/experiments/` 에 기록한다. 예측은 측정 전에 적는다.

## 사후 검증 (2026-08-16 측정 후 추가)

> 측정 기록: [v2-3 커서 페이징](../experiments/2026-08-16-v2-cursor-pagination.md)
>
> **결정은 유지한다. 그러나 배경 절의 근거 하나가 틀렸다.**
> 근거가 틀렸는데 결론이 맞은 경우이므로, 적어 두지 않으면 같은 오류를 반복한다.

### 맞은 것

| 예측 | 실측 |
| --- | --- |
| 요청당 훑는 행 1,345 → 약 41 | **43** ✅ |
| 깊은 페이지가 첫 페이지와 같은 비용이 된다 | OFFSET 9000 위치에서 13.97ms → **0.23ms** (62배) ✅ |
| 디스크 정렬 소멸 | temp 2,352kB → **0** ✅ |
| 행 값 비교가 인덱스를 탄다 | `Index Cond` 진입 확인. OR 전개 대비 **88배** ✅ |

### 틀린 것 ★

배경 절에 이렇게 썼다.

> "**`count` 가 DB CPU 의 대부분을 태우고 있다**" (요청당 1,345행 중 ~1,300행 = 96%)

**틀렸다.** count 를 제거한 결과:

```
행/요청     1,363 → 43      (97% 감소)
DB CPU      165% → 150%     (9% 감소만)
점유 시간   7.4ms → 7.6ms   (변화 없음)
피크 RPS    1,341 → 1,318   (변화 없음)
```

**행 점유율(96%)을 CPU 점유율로 바꿔 읽은 것이 오류다.**

측정값으로 쿼리 1회당 DB CPU 를 역산하면 원인이 드러난다:

```
OFFSET : 1,341 RPS × 22쿼리 = 29,502 쿼리/초  →  55.9 μs/쿼리
커서   : 1,318 RPS × 21쿼리 = 27,678 쿼리/초  →  54.2 μs/쿼리
```

쿼리가 1,300행을 보든 20행을 보든 **1회당 비용이 같다.**
비용은 행이 아니라 **파싱·계획·실행·프로토콜 왕복**에 붙어 있다.

```
요청당 쿼리 22개
├─ 목록      1개
├─ count     1개  ← 제거함 (4.5%)  → DB CPU 9% 감소. 계산과 일치
└─ N+1      20개  ← 91% ★
```

count 는 **행의 96% 였지만 쿼리의 4.5%** 였다.

> **셰어드 버퍼에 있는 인덱스라면 "훑는 행 수"는 비용의 대리지표가 되지 못한다.**
> v1 에서는 디스크·풀스캔 20만 행이라 행 수가 곧 비용이었고, 그 직관을 그대로 끌고 온 것이 오류였다.

### 결과적으로 우선순위 판단이 틀렸다

이 ADR 은 커서 페이징을 N+1 제거보다 **먼저** 하는 근거로 쓰였다.
`docs/01-roadmap.md` 의 원래 순서(인덱스 → **N+1** → 커서)가 맞았다.

다만 순서가 바뀐 대가는 크지 않다. 커서의 이득(깊은 페이지, 데이터 증가 내성)은 실측으로 확인됐고,
무엇보다 **이 실험이 진짜 병목을 특정해 주었다.** 다음 개선의 예측이 이제 계산으로 나온다:

```
N+1 제거  →  요청당 쿼리 21개 → 1개
          →  예상 DB CPU 150% → 15% 부근
          →  예상 점유 7.6ms → 1ms 부근
```

### 결정을 유지하는 이유

- 깊은 페이지 62배 개선은 **인덱스로는 고칠 수 없던 문제**였다 (v2-1 에서 확인)
- 리뷰가 10배로 늘면 count 비용도 10배가 되지만 커서는 변하지 않는다.
  지금은 인덱스 1,300 엔트리라 싸지만, 13,000 엔트리가 되면 행 수가 실제로 비용을 지배하기 시작한다
- 되돌리는 비용이 이득보다 크다. OFFSET 경로는 어차피 남아 있다
