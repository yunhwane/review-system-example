# 단계별 로드맵

각 단계는 **하나의 병목만** 다룹니다. 순서를 지키세요. v3(캐시)을 먼저 하면 v2(인덱스)의 효과를 영원히 측정할 수 없습니다.

각 단계 공통 절차:

1. 이전 단계의 부하 테스트를 그대로 재실행해 베이스라인을 확인한다
2. **가설을 먼저 문서에 적는다** (몇 RPS까지 오를 것 같은가, 왜?)
3. 한 가지만 변경한다
4. 같은 부하 테스트를 재실행한다
5. 예측과 실측의 차이를 `docs/experiments/`에 기록한다 — 여기가 학습의 본체다

---

## v1 — 베이스라인 (최적화 없음)

**상태: 코드가 이미 이 상태입니다. 측정만 하면 됩니다.**

일부러 넣어 둔 문제들:

| 문제 | 위치 | 증상 |
| --- | --- | --- |
| `product_id` 인덱스 없음 | `infra/postgres/init/01-schema.sql` | 리뷰 목록 조회마다 풀스캔 |
| N+1 쿼리 | `ReviewService.getReviews()` | 리뷰 20건 조회에 쿼리 21번 |
| OFFSET 페이징 | 동일 | 뒷 페이지로 갈수록 느려짐 |
| 요약 통계 매번 집계 | `ReviewService.getSummary()` | 요청마다 10만 건 집계 |
| 커넥션 풀 10 (기본값) | `application.yml` | 동시성 상한 |

**할 일**

```bash
k6 run load-test/k6/browse.js          # 계단식 부하로 한계점 찾기
k6 run load-test/k6/summary.js         # 집계 API 따로 측정
```

**측정할 것**

- 한계 RPS (p95가 200ms를 넘기 시작하는 지점)
- 그때의 CPU, `hikaricp_connections_pending`, `hikaricp_connections_active`
- 페이지 1과 페이지 500의 응답 시간 차이 (OFFSET 페이징의 대가)

**합격 기준**: 없음. **무너뜨리는 게 목적입니다.** 무너지는 지점과 그때의 지표 모양을 설명할 수 있으면 통과.

**핵심 질문**: CPU가 남는데 왜 느린가?

## v2 — 쿼리/코드 최적화

돈이 가장 적게 드는 최적화입니다. 서버를 늘리기 전에 여기부터 합니다.

**변경 내용** (하나씩 따로 측정하세요)

1. `CREATE INDEX idx_review_product_created ON review (product_id, created_at DESC);`
   → 복합 인덱스의 컬럼 순서가 왜 이 순서인지 설명할 수 있어야 합니다
2. N+1 제거: `@EntityGraph` 또는 fetch join
3. OFFSET → 커서(keyset) 페이징: `WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`
4. 응답 DTO에서 불필요한 필드 제거 (6절 대역폭 계산과 연결)

**측정할 것**: 각 변경 전후의 한계 RPS와 p95. `EXPLAIN ANALYZE` 결과를 문서에 붙여 넣으세요.

**예상**: 250 RPS → 1,500~3,000 RPS. **인덱스 한 줄이 서버 여러 대 값을 합니다.**

**핵심 질문**: 인덱스를 걸었는데 안 빨라졌다면, `EXPLAIN`에서 무엇을 확인해야 하나?

## v3 — 캐시 (Redis)

**변경 내용**

1. 리뷰 요약(평점 평균/분포)을 Redis에 캐싱 — 계산이 무겁고 자주 안 바뀌는, 캐시의 교과서적 대상
2. 인기 상품의 1페이지 캐싱
3. TTL 설계, 리뷰 작성 시 무효화 전략

**부딪혀 볼 것**

- **캐시 스탬피드**: 인기 키의 TTL이 만료되는 순간 수천 요청이 동시에 DB로 갑니다.
  대응(뮤텍스/논리적 만료/확률적 조기 갱신)을 적용 전후로 측정하세요.
- **핫키**: 시드 데이터는 지프 분포라 소수 상품에 리뷰가 몰려 있습니다. 캐시 적중률이 상품별로 다릅니다.
- **적중률과 효과의 비선형성**: 적중률 90% → 99%가 DB 부하를 10배 줄입니다 (미스가 10%→1%).

**측정할 것**: 캐시 적중률, DB 쿼리 수 감소량, 적중/미스 각각의 p95

**핵심 질문**: 적중률 50%짜리 캐시는 붙일 가치가 있나? 어떤 조건에서 오히려 손해인가?

## v4 — 리소스 튜닝 (풀 · 스레드 · JVM)

**변경 내용**

1. HikariCP 풀 크기: 10 → 20 → 50 → 100. **크게 하면 계속 빨라질까?**
2. 톰캣 스레드 수 조정
3. JVM 힙 크기와 GC 로그 관찰

**핵심 함정**

풀을 무한정 키우면 오히려 느려집니다. DB CPU 코어 수를 넘어서면 컨텍스트 스위칭과 락 경합만 늘어납니다.
HikariCP 문서의 권장 공식을 직접 검증해 보세요:

```
풀 크기 = (코어 수 × 2) + 유효 디스크 수
```

**측정할 것**: 풀 크기별 한계 RPS 곡선. **최적점이 있고 그 뒤로 꺾인다**는 걸 그래프로 확인하세요.

**핵심 질문**: 풀 크기를 100으로 올렸더니 처리량이 줄었다. 왜인가?

## v5 — 스케일아웃

**변경 내용**

1. 앱 인스턴스 3대 + Nginx 로드밸런서
2. 무상태(stateless) 검증 — 인스턴스별 로컬 상태가 있으면 여기서 깨집니다
3. Prometheus가 여러 인스턴스를 함께 스크레이프하도록 구성

**부딪혀 볼 것**

- 앱 3대 × 커넥션 풀 50 = 150 커넥션 → **Postgres `max_connections` 기본 100을 넘깁니다.** 여기서 터집니다.
- 대응: 풀 크기 재산정 또는 PgBouncer 도입
- **처리량이 3배가 되지 않습니다.** 왜 안 되는지가 이 단계의 학습 내용입니다.

**측정할 것**: 1대 / 2대 / 3대의 한계 RPS. 선형 확장 대비 실제 효율(%)

**핵심 질문**: 앱을 10대로 늘리면 무엇이 다음 병목이 되나?

---

## v6 — 읽기/쓰기 분리와 비동기화

**변경 내용**

1. Postgres 스트리밍 복제로 read replica 구성, 읽기 트래픽을 복제본으로 라우팅
2. 복제 지연(replication lag) 관찰 — **"방금 쓴 리뷰가 안 보인다"** 문제를 직접 재현
3. `helpful_count` 증가 같은 쓰기를 큐로 비동기 처리, 배치 반영

**측정할 것**: 복제 지연 시간, 읽기 부하 분산 비율, 비동기화 후 쓰기 응답 시간

**핵심 질문**: 리뷰 작성 직후 목록에 안 나타나도 되는가? 이건 기술 문제인가 제품 결정인가?
(정답: 제품 결정입니다. **아키텍처 트레이드오프는 기술만으로 결정할 수 없습니다.**)

## 부록 — 별도 축으로 해 볼 실험

로드맵과 독립적으로, 궁금할 때 하면 되는 것들:

| 실험 | 배우는 것 |
| --- | --- |
| 시드를 1,000만 건으로 늘리기 | 데이터가 메모리를 넘을 때 무엇이 달라지나, 파티셔닝이 언제 필요해지나 |
| k8s(kind) + HPA | 오토스케일링의 반응 지연, 스케일 아웃이 늦는 이유 |
| OpenTelemetry + Jaeger | 요청 하나가 어디서 시간을 쓰는지 구간별 추적 |
| 장애 주입 (DB 중단, 지연 삽입) | 타임아웃·서킷브레이커·graceful degradation |
| 리뷰 검색 (전문 검색) | RDB 전문 검색의 한계와 검색 엔진 분리 시점 |
