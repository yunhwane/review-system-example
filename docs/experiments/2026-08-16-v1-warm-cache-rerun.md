# 실험: v1 재측정 — 캐시가 데워진 상태의 한계

- 날짜: 2026-08-16
- 단계: v1
- 변경 사항: **없음** (코드·설정 무변경). 인프라를 29시간 연속 기동한 상태에서 베이스라인을 다시 측정

> 이 실험의 목적은 개선이 아니라 **재현성 확인**입니다.
> 코드를 한 줄도 바꾸지 않고 같은 테스트를 돌렸을 때 숫자가 얼마나 흔들리는지,
> 그리고 **무엇이 흔들리지 않는지**를 확인합니다.

## 1. 가설 (측정 전에 작성)

> ⚠️ 이 측정은 "인프라 기동 확인"에서 출발했기 때문에 **전용 가설을 새로 쓰지 않았습니다.**
> 대신 이미 문서에 남아 있던 두 개의 사전 예측을 가설로 삼습니다. 둘 다 측정 전에 작성된 것입니다.

- 예상 한계 RPS:
  - `docs/00-capacity-planning.md` 4절 예측 = **250 RPS** (`10 ÷ 0.04s`)
  - `2026-08-15-v1-baseline.md` 실측 = **136 RPS** (점유 시간 73ms 기준)
- 예상 p95: 200ms 초과 (k6 threshold 실패)
- 그렇게 예상한 이유:
  ```
  한계 RPS = 커넥션 풀 크기 ÷ 커넥션 점유 시간
  ```
- 병목이 될 것으로 보는 지점: **HikariCP 커넥션 풀 (크기 10)**

| VU | RPS | p50 | p95 | p99 | pending | active | 획득대기 | 점유 | 톰캣busy | 앱CPU | 초당읽은행 |

**한계점**: VU 200과 400 사이 ≈ **VU 300 / 294 RPS**

계산으로 좁히면:

```
풀이 감당하는 상한        = 10 ÷ 0.034s = 294 RPS
닫힌 루프(k6)의 요구량    = VU ÷ (think 1s + 응답시간)
포화 조건                 VU ÷ (1 + 0.05) > 294  →  VU > 309
```

VU 200은 요구량이 ~190 RPS라 상한(294) 아래여서 건강했고,
VU 400은 요구량이 ~400 RPS로 상한을 넘어서면서 포화됐습니다.

> think time을 1초로 줄인 테스트이므로 **VU 1명 ≈ 현실 사용자 30명**입니다.
> VU 300 ≈ **현실 동시 사용자 9,000명**.

### p95의 분해

```
p95 447ms
├─ 커넥션 획득 대기  368ms  (82%)  ← 줄 서서 기다린 시간
├─ 실제 DB 작업       34ms  ( 8%)
└─ 나머지            ~45ms  (10%)
```

### 검산 1 — Little's Law (처리량)

```
한계 RPS = 커넥션 수 ÷ 점유 시간 = 10 ÷ 0.034s = 294 RPS
실측 피크 = 294.4 RPS
```

### 검산 2 — 대기 행렬 (응답 시간)

```
획득 대기 = pending ÷ (풀 크기 ÷ 점유 시간)
          = 118 ÷ 294
          = 0.40초 = 400ms
실측 획득 대기 = 331~368 ms
```

**pending과 점유 시간만으로 응답 시간을 예측할 수 있습니다.**

## 5. 분석

### 실제 병목

**HikariCP 커넥션 풀.** 베이스라인과 동일합니다.
지표 모양이 `docs/02-monitoring.md` 4절 첫 번째 줄과 정확히 일치했습니다 —
**"앱 CPU 낮음 + DB CPU 낮음 + pending 높음 = 커넥션 풀 고갈"**.

톰캣 busy 159 중 실제로 일한 건 10개(active)뿐입니다. 나머지 148개는 **서 있기만 했습니다.**
앱 CPU 8%가 그 증거입니다 — 대기 중인 스레드는 CPU를 쓰지 않습니다.

### 가설과 다른 점, 왜 달랐나

| | 예측(00-capacity) | 베이스라인(8/15) | **오늘(8/16)** |
| --- | --- | --- | --- |
| 점유 시간 | 40ms (가정) | 73ms | **34ms** |
| 한계 RPS | 250 | 136 | **294** |
| p95 | — | 863ms | **448ms** |
| `10 ÷ 점유시간` | 250 | 137 | 294 |
| 실측 | — | 136 ✓ | 294 ✓ |

**코드를 한 줄도 바꾸지 않았는데 처리량이 2.2배가 됐습니다.**

원인은 **Postgres 캐시가 데워진 것**으로 보입니다.
`shared_buffers=256MB` + OS 페이지 캐시에 리뷰 100k / 회원 50k가 대부분 올라온 상태였고,
베이스라인은 컨테이너를 막 띄운 cold 상태였습니다.
특히 N+1로 나가는 회원 조회 20건이 전부 캐시에서 해결되면서 점유 시간이 73ms → 34ms로 줄었습니다.

초당 읽은 행이 2,200(베이스라인) → 5,330(오늘)으로 늘어난 것도 같은 이야기입니다 —
디스크가 아니라 메모리에서 읽으니 **더 많이, 더 빨리** 읽을 수 있었습니다.

### 흔들린 것과 흔들리지 않은 것

이 실험에서 가장 중요한 결과입니다.

| | |
| --- | --- |
| **흔들림** | 절대값 — RPS(136 ↔ 294), p95(863 ↔ 448), 점유 시간(73 ↔ 34) |
| **안 흔들림** | **관계 — `한계 RPS = 풀 크기 ÷ 점유 시간`이 두 번 다 소수점까지 맞았다** |
| **안 흔들림** | 병목의 정체 (커넥션 풀), 지표의 모양 (active 평평 + pending 폭발 + CPU 낮음) |

> **대시보드에서 읽어야 할 것은 숫자가 아니라 관계입니다.**
> 절대값만 기록한 실험은 다음 주에 재현되지 않습니다.

### 이 데이터가 반박하는 판단

| 흔한 판단 | 왜 틀렸나 |
| --- | --- |
| "느리니까 서버를 늘리자" | 앱 CPU 8%. 25대로 늘리면 DB에 250 커넥션 요구 → `max_connections=100`에서 터짐 |
| "CPU 좋은 장비로 업그레이드" | CPU를 안 쓰고 있는데 CPU를 늘림 |
| "톰캣 스레드를 500으로" | pending이 148 → 400이 될 뿐. **줄만 길어지고 창구는 그대로** |
| "p95 447ms니 DB가 느리다" | 점유 시간은 34ms로 전 구간 일정. DB는 느려지지 않았음 |

### 측정 신뢰도 주의

- **시스템 CPU가 87.7%까지 올라갔습니다** (앱은 8%). k6를 같은 노트북에서 돌린 대가입니다.
  이번엔 pending 148 / 획득대기 331ms가 명확해서 진단이 흔들리지 않지만,
  v2에서 RPS가 2,000 부근까지 올라가면 `docs/02-monitoring.md` 4절 **마지막 줄
  (부하 도구가 병목)** 을 반드시 의심해야 합니다.
- 캐시 상태가 결과를 2배 이상 바꿉니다. **v2 이후 실험은 `down -v` 후 동일한 워밍업 절차로**
  조건을 맞춰야 비교가 성립합니다.

## 6. 결론과 다음 행동

기준 시나리오(평상시 3,333 RPS)와 비교하면:

```
현재 294 RPS → 목표의 8.8%
필요 서버 대수: 3,333 ÷ 294 ≈ 11.3대
```

베이스라인의 25대에서 11대로 줄었지만, **캐시가 데워진 덕분이지 설계가 나아진 게 아닙니다.**
리뷰 10만 건짜리 서비스에 서버 11대는 여전히 잘못된 설계입니다.

### 레버는 두 개뿐

```
한계 RPS = 풀 크기 ÷ 점유 시간
              ↑         ↑
            분자       분모
```

| 레버 | 조작 | 기대치 | 단계 |
| --- | --- | --- | --- |
| 분자 | 풀 10 → 50 | 294 → 1,470 | v4 |
| **분모** | **점유 34ms → 5ms** | **294 → 2,000** | **v2** |

**분모가 먼저입니다.** 분자를 늘리는 건 부하를 DB로 밀어내는 것일 뿐이고,
`max_connections=100`이라 앱을 여러 대로 늘리면(v5) 거기서 먼저 터집니다.
분모를 줄이면 DB가 하는 일 자체가 줄어듭니다 — 오늘 초당 5,330행을 읽었는데 인덱스 하나면 20행이면 됩니다.

### 다음에 바꿀 한 가지 (v2, 각각 따로 측정)

1. `CREATE INDEX idx_review_product_created ON review (product_id, created_at DESC);`
   → 풀스캔 제거. 점유 시간이 가장 크게 줄어들 것으로 예상
2. N+1 제거 (fetch join / `@EntityGraph`) → 요청당 쿼리 22개 → 2개
3. OFFSET → 커서 페이징 → 뒷페이지 디스크 정렬 제거

**한 사이클에 하나씩. 두 개를 동시에 바꾸면 어느 쪽이 효과를 냈는지 알 수 없습니다.**
