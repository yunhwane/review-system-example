# 실험: v2-3 — 커서(keyset) 페이징 도입

- 날짜: 2026-08-16
- 단계: v2
- 변경 사항: **페이징 방식 하나.** OFFSET → 커서. N+1 과 인덱스는 그대로 둠

> 설계 근거: [ADR 0003](../adr/0003-cursor-pagination.md)
> 직전 측정: `2026-08-16-v2-loadgen-thinktime.md`

> **결론부터: 가설이 크게 틀렸다.**
> 훑는 행을 97% 줄였는데 **처리량이 전혀 오르지 않았다.**
> 틀린 지점에서 배운 게 이 실험의 본체다.

## 1. 가설 (측정 전에 작성)

| 항목 | 예측 | 근거 |
| --- | --- | --- |
| 요청당 훑는 행 | 1,345 → **약 41** | 목록 21 + N+1 20. count ~1,300 소멸 |
| DB CPU (VU 400) | 140% → **50~70%** | 행 수가 97% 줄어드니 CPU 도 크게 줄 것 |
| 커넥션 점유 | 7.1ms → **4~5ms** | count 0.97ms 소멸 + DB 여유로 각 쿼리도 빨라짐 |
| **한계 RPS** | 1,404 → **약 2,200** | `10 ÷ 0.0045s` |
| OFFSET 재측정 | ~1,400 재현 | 같은 코드·같은 조건 |

**부하가 또 모자랄 가능성도 함께 적어 뒀다:**
VU 400 / think 0.2초의 최대 요구는 1,905 RPS 인데 새 천장 예측이 2,200 이므로,
RPS 가 ~1,900 에서 VU 상한에 걸리고 `pending` 이 0 에 머물 수 있다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 앱 | Spring Boot 4.1 / Java 21, **재시작함** (새 엔드포인트 반영) |
| DB | Postgres 17 (Docker), `shared_buffers=256MB`, `max_connections=100` |
| 커넥션 풀 | HikariCP **10** (변경 없음) |
| 톰캣 스레드 | 200 (변경 없음) |
| 인덱스 | `idx_review_product_created` 있음 (변경 없음) |
| **N+1** | **그대로 있음** (아직 안 고침) |
| 데이터 | 상품 1,000 / 회원 50,000 / 리뷰 100,001 |
| 부하 도구 | k6 v2.2.0, **think time 0.2초** (v2-2 와 동일) |

**측정 순서**: 워밍업 60초 → `browse.js`(OFFSET) 6분 30초 → `browse-cursor.js`(커서) 6분 30초.

앱을 재시작했으므로 JIT·커넥션 상태가 v2-2 와 다르다.
그래서 **같은 프로세스에서 OFFSET 을 다시 재고** 그 값을 비교 기준으로 삼았다.
두 엔드포인트를 공존시킨 [ADR 0003](../adr/0003-cursor-pagination.md) 의 결정이 여기서 값을 했다.

> ⚠️ **`bootRun` 은 `-XX:TieredStopAtLevel=1` 로 뜬다.** C2 JIT 이 꺼진 상태다.
> 지금까지의 모든 측정이 같은 조건이라 비교는 유효하지만,
> **절대 수치는 프로덕션 JVM 보다 비관적이다.** 이번에 처음 확인해서 기록해 둔다.

## 4. 결과

### 사전 검증 — 실행 계획 (부하 전)

| 쿼리 | 시간 | 버퍼 | 비고 |
| --- | --- | --- | --- |
| 커서 첫 페이지 | 0.31 ms | 37 | Index Scan + Incremental Sort |
| **커서 다음 페이지 (행 값 비교)** | **0.23 ms** | **25** | `Index Cond` 에 `created_at <=` 가 들어감 |
| 같은 조건을 OR 로 전개 | **20.02 ms** | **7,421** | `Filter` 로 밀림, `Rows Removed: 7,368` |
| OFFSET 9000 (기존) | 13.97 ms | 7,767 + **temp 2,352kB** | Parallel Seq Scan + 디스크 정렬 |

**행 값 비교 `(a,b) < (x,y)` vs OR 전개 = 88배 차이.**
Postgres 는 OR 을 인덱스 탐색으로 접지 못한다. JPQL 이 행 값 비교를 지원하지 않아
네이티브 쿼리를 쓴 이유가 이것이다.

**깊은 페이지는 커서가 OFFSET 대비 62배 빠르고 디스크 정렬이 사라졌다.**

## 5. 분석

### 훑는 행을 97% 없앴는데 처리량이 그대로다

```
행/요청     1,363 → 43     (97% 감소)
행/초       1.83M → 56K    (32배 감소)
점유 시간   7.4ms → 7.6ms  (변화 없음)
DB CPU      165% → 150%    (9% 감소)
피크 RPS    1,341 → 1,318  (변화 없음)
```

**훑는 행 수는 병목이 아니었다.**

### 비용은 행이 아니라 쿼리 횟수에 붙어 있다

측정값으로 쿼리 1회당 DB CPU 를 역산하면:

```
OFFSET : 1,341 RPS × 22쿼리 = 29,502 쿼리/초  →  1.65코어 ÷ 29,502 = 55.9 μs/쿼리
커서   : 1,318 RPS × 21쿼리 = 27,678 쿼리/초  →  1.50코어 ÷ 27,678 = 54.2 μs/쿼리
```

**쿼리 1회당 비용이 거의 같다.** 그 쿼리가 1,300행을 보든 20행을 보든 상관없이.

요청당 쿼리 구성은 이렇다:

```
요청당 쿼리 22개
├─ 목록      1개
├─ count     1개  ← 이번에 제거 (4.5%)
└─ N+1      20개  ← 91% ★
```

count 는 **행의 96% 였지만 쿼리의 4.5%** 였다. 그래서 DB CPU 가 딱 9% 줄었다.
셰어드 버퍼에 올라온 인덱스 1,300 엔트리를 훑는 건 0.97ms 로 거의 공짜였고,
진짜 비용은 **파싱·계획·실행·프로토콜 왕복 오버헤드**였다.

> **교훈: "훑는 행 수"를 비용의 대리지표로 쓰면 안 된다.**
> 디스크에서 읽어야 하는 행이라면 행 수가 비용을 지배하지만,
> **메모리에 있는 인덱스라면 행 수보다 쿼리 횟수가 지배한다.**
> v1 에서는 풀스캔 20만 행이라 행 수가 곧 비용이었다. 그 직관을 그대로 끌고 온 게 오류였다.

### 그래서 v2-2 의 결론이 틀렸다

`2026-08-16-v2-loadgen-thinktime.md` 5절에 이렇게 썼다:

> "**DB CPU 140% 의 대부분이 `count(*)` 다.** 다음 개선의 1순위 근거가 됐다."

**이 문장은 틀렸다.** 행 점유율(96%)을 CPU 점유율로 바꿔 읽은 것이다.
실제로 count 를 없애자 DB CPU 는 9% 줄었다.

같은 오류가 [ADR 0003](../adr/0003-cursor-pagination.md) 배경 절에도 들어갔고,
그 결과 **커서 페이징을 N+1 보다 먼저 하는 잘못된 우선순위**를 골랐다.
`docs/01-roadmap.md` 의 원래 순서(인덱스 → N+1 → 커서)가 맞았다.

### 커서 페이징이 헛수고였나 — 아니다

측정으로 확인된 이득은 그대로 남는다.

| | OFFSET | 커서 |
| --- | --- | --- |
| 깊은 페이지 (OFFSET 9000 위치) | 13.97ms, 디스크 정렬 2,352kB | **0.23ms, 디스크 없음** |
| 리뷰가 10배 늘면 count 비용 | **10배** | **변화 없음** |
| 요청당 훑는 행 | 1,363 | **43** |

**지금 부하에서 처리량이 안 오른 것이지 개선이 없는 게 아니다.**
현재 병목(커넥션 풀 + 쿼리 왕복)이 워낙 커서 가려졌을 뿐이다.
N+1 을 없애 쿼리 왕복이 사라지면 이 이득이 드러난다.

또한 커서는 **데이터가 늘어도 비용이 일정**하다. 지금은 리뷰가 10만 건이라
count 가 인덱스 1,300 엔트리로 끝나지만, 100만 건이면 13,000 엔트리가 되고
그때는 행 수가 실제로 비용을 지배하기 시작한다.

### 커서가 오히려 조금 느리게 나온 이유

p95 118.97ms(OFFSET) vs 160.26ms(커서). 두 가지가 섞여 있다.

1. **VU 50 구간의 콜드 스타트.** 커서 경로는 그 시점까지 거의 실행된 적이 없어
   JIT 컴파일이 안 된 상태였다 (점유 12.7ms, p50 25ms — 다른 구간의 2배).
   OFFSET 은 워밍업 60초에서 이미 데워져 있었다. **워밍업이 한쪽에만 적용된 것이 설계 결함이다.**
2. **VU 400 구간에서는 사실상 같다** (152ms vs 160ms, RPS 1,318 vs 1,341).
   둘 다 커넥션 풀에 막혀 있어 차이가 나타날 여지가 없다.

**다음부터는 두 경로 모두 워밍업해야 한다.**

### 측정 시나리오의 한계 (기록)

`browse-cursor.js` 의 이어보기 비율이 **10%** 로 나왔다 (목표 20%).
VU 가 그 상품의 커서를 아직 안 갖고 있으면 첫 페이지로 떨어지기 때문이다.
즉 커서 쪽이 OFFSET 쪽보다 **깊은 페이지를 덜 때렸다** — 커서에 유리한 편향인데도
결과가 같았다는 점은 위 결론을 오히려 강화한다.

## 6. 결론과 다음 행동

```
커서 페이징 도입
  → 요청당 훑는 행  1,363 → 43   (97% 감소)
  → 깊은 페이지     13.97ms → 0.23ms  (62배)
  → 처리량          1,341 → 1,318 RPS  (변화 없음)
  → 병목은 그대로: 커넥션 풀 + 쿼리 왕복 21회
```

**이 실험의 가장 큰 수확은 개선이 아니라 병목의 재식별이다.**

### 다음에 바꿀 한 가지: N+1 제거

이제 예측이 뚜렷하다.

```
fetch join 으로 N+1 제거  →  요청당 쿼리 21개 → 1개  (95% 감소)

예상 DB CPU    150% → 15% 부근      (54μs/쿼리 × 1,318 × 1)
예상 점유 시간 7.6ms → 1ms 부근     (현재 7.6ms ÷ 21쿼리 = 0.36ms/왕복)
예상 한계 RPS  1,318 → 훨씬 위      (그때는 다른 게 병목이 될 것)
```

**부하 도구가 또 모자랄 것이 거의 확실하다.** VU 400 / think 0.2초의 상한이 1,905 RPS 인데
예상 천장이 그보다 한참 위다. N+1 측정 때는 **think time 을 더 줄이거나 VU 를 올려서** 시작해야 한다.

### 측정 절차에 추가된 규칙

1. **A/B 비교 시 두 경로를 모두 워밍업한다.** 이번에 한쪽만 데워서 콜드 스타트가 섞였다.
2. **"훑는 행 수"를 비용의 대리지표로 쓰지 않는다.** 캐시에 있는 데이터라면
   쿼리 횟수가 지배한다. 행 수와 쿼리 수를 **둘 다** 본다.
3. **`bootRun` 은 `-XX:TieredStopAtLevel=1`** 이다. 절대 수치는 프로덕션보다 비관적이다.

### 이 실험으로 쓸 ADR

[ADR 0003](../adr/0003-cursor-pagination.md) 을 **정정**한다. 결정 자체(커서 채택)는 유지한다 —
깊은 페이지와 데이터 증가에 대한 이득은 실측으로 확인됐다.
다만 **"count 가 DB CPU 의 대부분"이라는 배경 절의 근거가 틀렸음**을 사후 절로 남긴다.
근거가 틀렸는데 결론이 맞은 경우이므로, 그 사실을 적어 두지 않으면 다음에 같은 오류를 반복한다.
