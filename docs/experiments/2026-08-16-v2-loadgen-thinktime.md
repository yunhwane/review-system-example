# 실험: v2-2 — 부하 시나리오 상향 (think time 1초 → 0.2초)

- 날짜: 2026-08-16
- 단계: v2
- 변경 사항: **부하 도구 설정 하나.** `THINK_TIME=1` → `0.2`. **시스템은 아무것도 바꾸지 않았다.**

```bash
k6 run -e THINK_TIME=0.2 load-test/k6/browse.js
```

> 직전 측정: `2026-08-16-v2-index-product-created.md`
>
> **이 실험은 시스템을 개선하지 않는다.** 직전 실험에서 부하가 모자라 한계점을
> 찾지 못했기 때문에, **측정 도구부터 고치는** 사이클이다.
> 측정할 수 없으면 다음 개선의 효과도 알 수 없다.

## 0. 왜 이 실험이 필요한가

직전 실험(v2-1) 결과가 이랬다:

```
피크 RPS 399.9,  pending 0,  active 0.3 (풀 10 중),  톰캣 busy 3 (max 200)
```

**모든 자원이 한가한데 RPS가 VU 상한에 정확히 붙어 있었다.**
399.9 = `400 ÷ (1초 + 0.007초)` — 이건 시스템의 한계가 아니라 **부하 도구의 상한**이다.

이 상태에서 N+1을 제거하든 커서 페이징을 넣든 결과는 똑같이 399 RPS로 나온다.
**개선의 효과를 측정할 수 없는 도구로는 개선을 할 수 없다.**

### 두 가지 방법 중 왜 think time인가

| | VU를 늘린다 | **think time을 줄인다** |
| --- | --- | --- |
| 설정 | VU 800/1600, think 1초 | VU 그대로, think 0.2초 |
| 1,600 RPS에 필요한 VU | 1,600개 | **340개** |
| k6 부담 | 4배 | 그대로 |
| 코드 수정 | 필요 (stages) | **불필요** (`THINK_TIME` env 이미 지원) |

**k6 자신이 병목이 되면 안 된다**는 제약이 선택을 결정했다.
같은 RPS를 1/4의 VU로 만들 수 있어서 부하 도구가 훨씬 편하다.
게다가 스크립트 수정이 필요 없으므로 **바뀐 변수가 정확히 하나**다.

### 환산이 바뀐다 (기록 필수)

`docs/00-capacity-planning.md`는 현실 think time을 30초로 가정한다.

```
think 1초   : VU 1 ≈ 현실 사용자  30명  → VU 400 ≈  12,000명
think 0.2초 : VU 1 ≈ 현실 사용자 150명  → VU 400 ≈  60,000명
```

**이 환산을 잊으면 "VU 400밖에 못 버티네"라는 잘못된 결론을 내리게 된다.**

## 1. 가설 (측정 전에 작성)

> 이 절은 테스트를 돌리기 **전에** 작성했다. 결과를 보고 고치지 않는다.

계산 근거:

```
요구 RPS = VU ÷ (think 0.2초 + 응답시간)
천장     = 커넥션 10 ÷ 점유 0.0062초 = 1,613 RPS   (v2-1 실측 점유 시간)
포화 VU  = 1,613 × 0.21 ≈ 340        → VU 200 과 400 사이에서 꺾인다
```

| VU | 요구 RPS | 예상 결과 | 예상 active |
| --- | --- | --- | --- |
| 50 | 238 | 여유 | 1.5 |
| 100 | 476 | 여유 | 3.0 |
| 200 | 952 | 여유, active 가 눈에 띄게 오름 | 5.9 |
| **400** | **1,905** | **천장 초과 → 포화.** RPS ~1,600 에서 평평, pending 상승 | **10 (천장)** |

- 예상 피크 RPS: **약 1,600**
- 예상 병목: **다시 HikariCP 커넥션 풀** (풀 크기는 그대로 10)
- 단, DB CPU 가 먼저 한계에 닿을 가능성도 있다 (초당 2백만 행 스캔 예상)

### 특히 확인하고 싶은 것 ★

> **포화되는데도 k6 threshold 는 통과할 것이다.**
>
> VU 400 에서 포화되면 `400 ÷ (0.2 + r) = 1,613` → **r ≈ 48ms** 로 수렴한다.
> p95 는 100~150ms 정도일 테니 **`p95 < 200ms` 를 통과한다.**
> 하지만 `active` 는 10 에 붙고 `pending` 은 쌓인다.
>
> **즉 "SLO 통과 = 여유 있음" 이 아니다.**
> 포화는 SLO 가 아니라 saturation 지표(`active`, `pending`)로만 보인다.
> `docs/02-monitoring.md` 2절이 "Saturation 이 가장 중요한데 가장 자주 빠진다" 고 한 게 이 상황이다.

### 측정 실패 시나리오 (미리 정해 둔다)

아래 모양이 나오면 **시스템이 아니라 k6 가 한계**다. 그때는 결과를 신뢰하지 않는다.

```
RPS 가 안 오름 + pending 0 + active 낮음 + 시스템 CPU 100% 부근
```

→ `docs/02-monitoring.md` 4절 마지막 줄.

## 5. 분석

### 실제 병목: 다시 커넥션 풀. 단, DB CPU 가 새로 올라왔다

VU 400 의 지표는 v1 과 같은 모양이다 — `active` 10 천장, `pending` 150, 획득 대기 77ms.
**풀 크기를 안 건드렸으니 당연하다.** 인덱스는 점유 시간을 줄였을 뿐 풀을 넓히지 않았다.

```
[v1]   점유 35ms   → 천장 10 ÷ 0.035 =   286 RPS
[v2-1] 점유 6.2ms  → 천장 10 ÷ 0.0062 = 1,613 RPS  (미검증)
[v2-2] 점유 7.1ms  → 천장 10 ÷ 0.0071 = 1,408 RPS  (검증됨)
```

**같은 병목(커넥션 풀)인데 천장이 5배 올라갔다.** 인덱스가 한 일이 정확히 이것이다.

새로 나타난 것은 **DB CPU** 다. v1·v2-1 에서는 DB 가 놀고 있었는데, 이번엔 계단마다 뚜렷이 오른다:

```
VU  50 :  25~35%
VU 100 :  41~51%
VU 200 :  89~95%   ← 1 코어를 다 씀
VU 400 : 137~144%  ← 1.4 코어
```

**DB 가 처음으로 진짜 일을 하기 시작했다.** 다음 병목의 후보다.

### 예측이 13% 빗나간 이유

예측 1,613 은 v2-1 의 점유 시간 6.2ms 를 그대로 쓴 값이다.
실제로는 부하가 3.5배로 오르자 점유 시간이 **6.2ms → 7.1ms** 로 늘었다.

**DB CPU 가 140% 까지 올라가면서 쿼리 하나하나가 조금씩 느려진 것이다.**
즉 `점유 시간`은 상수가 아니라 **부하의 함수**다.

> **교훈: 저부하에서 잰 점유 시간으로 고부하의 천장을 예측하면 낙관적으로 틀린다.**
> 자원이 포화에 가까워질수록 단위 작업 시간은 늘어난다.

### ★ 포화됐는데 SLO 는 통과했다 — 예측 적중

이번 실험에서 가장 중요한 결과다.

```
k6 threshold  p95 < 200ms   →  99.2ms   ✅ 통과
VU 400 구간   p95            →  128ms    ✅ 200ms 아래
```

그런데 같은 시점의 saturation 지표는:

```
active   10.0 / 10    ← 풀이 100% 소진, 천장에 붙어 평평
pending  150          ← 150 개 스레드가 커넥션을 기다리며 서 있음
톰캣busy 160 / 200    ← 그 중 실제로 일하는 건 10 개
획득대기 77ms         ← 응답 128ms 의 60%가 줄서기
요구 1,905 vs 실측 1,401  ← 요구의 74% 밖에 처리 못 함
```

**SLO 는 초록불인데 시스템은 이미 포화 상태다.**

이유는 산수다. 포화되면 닫힌 루프가 `RPS = VU ÷ (think + 응답)` 에서 균형을 찾는다:

```
1,401 = 400 ÷ (0.2 + r)   →   r ≈ 85ms
```

**think time 이 0.2초라서 응답이 85ms 만 돼도 균형이 맞는다.**
think time 을 더 줄이거나 VU 를 더 올렸다면 이 균형점이 올라가 SLO 도 깨졌을 것이다.

> **"SLO 통과 = 여유 있음" 이 아니다.**
> SLO 는 사용자가 아픈지를 알려주고, saturation 지표는 **얼마나 더 버틸 수 있는지**를 알려준다.
> 둘은 다른 질문이고, 둘 다 봐야 한다.
> `docs/02-monitoring.md` 2절의 "Saturation 이 가장 중요한데 가장 자주 빠진다" 가 이 상황이다.

이건 알림 설계에도 그대로 적용된다. p95 알림만 걸어 두면 **이 상태를 못 잡는다.**

### 여전히 count 쿼리가 DB 를 태우고 있다

VU 400 에서 초당 1.89M 행. 요청당으로 환산하면:

```
1,885,328 ÷ 1,401 = 1,345 행/요청
```

v2-1 의 1,342 행/요청과 **똑같다.** 부하만 3.5배가 됐을 뿐 요청당 하는 일은 그대로다.
내역도 그대로다 — 목록 20 행 + member N+1 20 행 + **count ~1,300 행**.

**DB CPU 140% 의 대부분이 `count(*)` 다.** 다음 개선의 1순위 근거가 됐다.

> ⚠️ **정정 (2026-08-16, v2-3 측정 후).** 위 문장은 **틀렸다.** 원문은 기록으로 남긴다.
>
> 실제로 count 를 제거해 보니 행은 97% 줄었지만 **DB CPU 는 9% 만 줄었다** (165% → 150%).
> 행 점유율(96%)을 CPU 점유율로 바꿔 읽은 것이 오류다.
> 셰어드 버퍼에 있는 인덱스를 훑는 비용은 거의 없고, 실제 비용은 **쿼리 1회당 약 55μs 의 왕복 오버헤드**다.
> count 는 행의 96% 였지만 **쿼리 22개 중 1개(4.5%)** 였다. 진짜 덩어리는 **N+1 20개(91%)** 다.
>
> 근거: [v2-3 커서 페이징](2026-08-16-v2-cursor-pagination.md)

## 6. 결론과 다음 행동

```
측정 도구만 고쳤다 (think 1초 → 0.2초)
  → 같은 시스템에서 399.9 RPS → 1,404.4 RPS 로 측정
  → 진짜 한계점을 처음으로 찾았다: 약 1,404 RPS
  → 병목은 여전히 커넥션 풀, 그러나 DB CPU 가 새 후보로 등장
```

기준 시나리오(평상시 3,333 RPS) 대비:

```
1,404 RPS → 목표의 42%
필요 서버 대수: 3,333 ÷ 1,404 ≈ 2.4대
```

```
서버 25대 (v1 베이스라인)
  → 11대 (warm 캐시)
  → 2.4대 (인덱스 한 줄)        ← 지금 여기, 처음으로 측정된 값
```

VU 400 ≈ 현실 동시 사용자 **60,000명**. 기준 시나리오 10만 명의 60% 를 한 대로 받았다.

- DB CPU 가 140% 로 다음 병목의 최유력 후보인데, 그 원인이 count 로 특정됐다
- N+1 은 왕복 횟수 문제라 점유 시간에 영향을 주지만, 현재 점유 7.1ms 중 DB 작업 자체가 지배적이다
- 커서 페이징은 **API 계약이 바뀌므로 ADR 이 필요하다** — 설계 결정 연습의 대상이기도 하다

### 측정 절차에 추가된 규칙

1. **`THINK_TIME` 을 실험 기록에 반드시 명시한다.** 이 값이 다르면 RPS 는 비교 불가다.
2. **점유 시간은 부하의 함수다.** 천장을 예측할 때 저부하에서 잰 값을 쓰면 낙관적으로 틀린다.
3. **DB CPU 는 `docker stats` 로 따로 잰다.** postgres-exporter 는 컨테이너 CPU 를 노출하지 않아
   Grafana 만 보면 놓친다. (대시보드 패널 추가 후보)

### 이 실험으로 쓸 ADR

없음 — 시스템을 바꾸지 않았다.
다만 **다음 실험(커서 페이징)은 ADR 대상**이다. API 응답 형식이 바뀌고,
"총 개수를 안 주는 페이징을 받아들일 것인가"라는 트레이드오프가 있다.
대안: OFFSET 유지 + count 캐시(v3), 근사 count(`reltuples`), 무한 스크롤 전환.
