# 실험: v2-4 — 열린 모델 전환과 계보 이어붙이기

- 날짜: 2026-08-16
- 단계: v2 (측정 도구)
- 변경 사항: **부하 모델 하나.** 닫힌 모델(`ramping-vus`) → 열린 모델(`ramping-arrival-rate`).
  **시스템은 아무것도 바꾸지 않았다.**
- 측정 4회: 스모크 / OFFSET / 커서 1차 / 커서 2차(시나리오 수정 후)

> 배경 문서: [docs/03-load-testing.md](../03-load-testing.md)
> 직전 측정: `2026-08-16-v2-cursor-pagination.md`

> **이 실험은 시스템을 개선하지 않는다.** 측정 모델을 바꾸는 사이클이다.
> 그리고 그 결과, **지금까지의 모든 측정이 사용자 경험을 과대평가하고 있었다**는 것이 드러났다.

## 0. 왜 필요한가

v2-3 까지의 모든 측정은 닫힌 모델이었다. 닫힌 모델에서는 VU 가 응답을 받아야 다음 요청을 보내므로,
**시스템이 느려지면 부하가 저절로 줄어든다.** 시스템이 스스로를 보호하는 셈이다.

실제 공개 트래픽은 그렇지 않다. 서버가 느려져도 새 사용자는 계속 들어오고,
느려진 만큼 새로고침까지 눌러서 오히려 부하가 늘어난다.

또 하나. 닫힌 모델은 **"요구한 만큼 못 냈다"를 말해주지 않는다.**
v2-1~v2-3 에서 매번 "부하가 모자란 건가, 시스템이 한계인가"를
`pending`·`active`·CPU 로 **추론**해야 했다. 추론이 필요하다는 것 자체가 도구가 잘못됐다는 신호다.

## 1. 가설 (측정 전에 작성)

| 항목 | 예측 | 근거 |
| --- | --- | --- |
| 처리량 천장 | **닫힌 모델과 같을 것 (~1,400 RPS)** | 천장은 `풀 10 ÷ 점유 7ms = 1,428`이 지배한다. 부하 모델과 무관하다 |
| p95 | **닫힌 모델보다 훨씬 나쁠 것** | 큐가 자동으로 줄지 않으므로 대기가 쌓인다 |
| `dropped_iterations` | **0 초과** | 요구 3,000 RPS > 천장 1,400 |
| 판정 | **C** (시스템 한계, 신뢰 가능) | `pending`/`active` 가 찰 것이므로 |

## 3. 실행 명령

```bash
# 스모크 (판정 로직 확인용)
k6 run -e MAX_RATE=300 load-test/k6/browse-arrival.js

# OFFSET
k6 run -e MAX_RATE=3000 -e WORST_RESPONSE=0.5 load-test/k6/browse-arrival.js

# 커서 (경로를 먼저 데운 뒤 — v2-3 에서 한쪽만 워밍업해 오염된 적이 있다)
k6 run -e MODE=cursor -e MAX_RATE=400 load-test/k6/browse-arrival.js          # 워밍업
k6 run -e MODE=cursor -e MAX_RATE=3000 -e WORST_RESPONSE=0.5 load-test/k6/browse-arrival.js
```

측정 시각: 21:54:20 ~ 22:15:50 (KST)

### ★ 뜻밖의 대조 실험 — 뒷페이지 비율을 20배 올려도 아무것도 안 변했다

```
커서 1차 (뒷페이지  1%) : 1,395 RPS, DB CPU 133%, 59K 행/초
커서 2차 (뒷페이지 20%) : 1,395 RPS, DB CPU 134%, 58K 행/초
```

**이것이 커서 페이징이 약속한 성질이다.** 깊은 페이지가 첫 페이지와 비용이 같으므로,
뒷페이지를 얼마나 때리든 결과가 변하지 않는다.
실행 계획에서 확인한 "OFFSET 9000 위치가 13.97ms → 0.23ms" 가 부하 상태에서도 성립한다는 뜻이다.

OFFSET 이었다면 이 비율이 성능에 직접 영향을 줬을 것이다.
**시나리오 실수가 뜻밖에 커서의 핵심 성질을 대조 실험으로 증명해 주었다.**

### DB CPU 감소폭이 두 측정에서 다르다 (9% vs 19%)

같은 변경(count 제거)인데 v2-3 에서는 165% → 150%(9%), 여기서는 165% → 134%(19%) 였다.
두 측정으로 모델을 맞추면:

```
DB CPU = 쿼리당 45μs + 행당 0.116μs

OFFSET: 22쿼리 × 45μs + 1,361행 × 0.116μs = 990 + 158 = 1,148 μs/요청
커서  : 21쿼리 × 45μs +    42행 × 0.116μs = 945 +   5 =   950 μs/요청
                                                    → 17% 감소 (실측 19%)
```

**v2-3 의 결론을 다듬어야 한다.** "쿼리 횟수가 지배한다" 는 방향은 맞지만,
count 쿼리 하나만 놓고 보면 **행 비용(151μs)이 쿼리 오버헤드(45μs)보다 크다.**
다만 나머지 21개 쿼리의 오버헤드 합(945μs)이 워낙 커서 전체적으로는 쿼리 수가 지배한다.

> ⚠️ **이 계수는 2점으로 맞춘 모델이라 신뢰구간이 넓다.**
> 같은 변경을 두 번 쟀는데 9% 와 19% 가 나온 것이 그 증거다.
> N+1 제거 측정에서 세 번째 점이 생기면 검증된다. **그때까지는 가설로만 취급할 것.**

## 5. 분석

### 처리량은 같고 지연은 10배다

**처리량 천장은 부하 모델과 무관하다.** 예측대로였다.

```
천장 = 커넥션 10 ÷ 점유 0.007초 = 1,428 RPS
닫힌 모델 1,341 / 열린 모델 1,425 — 둘 다 여기에 붙어 있다
```

**하지만 사용자가 겪는 지연은 10배 차이다. 그리고 닫힌 모델은 이걸 보여줄 방법이 없다.**

### p95 1,627ms 의 정체 — 또 Little's Law

```
응답시간 = 대기 중인 요청 수 ÷ 처리율
        = 2,250 ÷ 1,428
        = 1.58초          (실측 p95 1.63초)
```

**2,250 은 `maxVUs` 다.** 즉 응답시간을 결정한 건 시스템이 아니라
**"큐가 얼마나 깊어질 수 있는가"** 였다.

요청 2,250개가 어디에 있었는지 분해하면:

```
├─    10개  DB 작업 중                    (active, 풀 크기)
├─   190개  톰캣 스레드에서 커넥션 대기      (pending, 스레드 200 한도)
├─   100개  accept 큐                     (accept-count)
└─ ~1,950개  OS 소켓 백로그 / 커넥션 대기
```

닫힌 모델에서 p95 가 160ms 였던 건 **VU 400 이 큐 깊이를 400 으로 묶어놨기 때문**이다.
`400 ÷ 1,428 = 0.28초` — think time 0.2초를 빼면 실측 160ms 와 대략 맞는다.

> **처리량 천장은 모델과 무관하게 같지만, 지연은 큐 깊이에 비례해 무한정 나빠진다.**
> 실제 공개 트래픽에는 `maxVUs` 같은 상한이 없다. 타임아웃이 걸릴 때까지 계속 깊어진다.

### ★★ Grafana 의 p95 와 사용자의 p95 가 10배 다르다

이 실험에서 가장 중요한 발견이다. **같은 시각, 같은 요청인데 두 p95 가 다르다.**

| 출처 | p95 | 무엇을 재는가 |
| --- | --- | --- |
| Prometheus `http_server_requests_seconds` (Grafana ② 패널) | **167 ms** | **톰캣 스레드가 요청을 집어든 뒤**부터 응답까지 |
| k6 `http_req_duration` | **1,627 ms** | **클라이언트가 보낸 순간**부터 받을 때까지 |
| 차이 | **1,460 ms** | **톰캣이 요청을 집어들기 전까지 기다린 시간** |

`http_server_requests` 는 **큐에서 기다린 시간을 재지 않는다.**
톰캣 스레드가 요청을 처리하기 시작할 때 타이머가 켜지기 때문이다.
accept 큐와 OS 소켓 백로그에서 기다린 1.46초는 **이 지표에 존재하지 않는다.**

전체 시간을 분해하면:

```
사용자가 겪은 1,627ms
├─ 1,460ms  accept 큐 + 소켓 백로그   ← 서버 지표에 안 잡힘 ★
├─   132ms  HikariCP 커넥션 대기      (pending 189 ÷ 1,428 RPS)
└─     7ms  실제 DB 작업              (점유 시간)
```

**서버가 아프다고 말하는 시간(167ms)보다 안 보이는 대기(1,460ms)가 9배 크다.**

### 그래서 서버 지표만 보면 이 상황을 놓친다

이 시점의 서버 쪽 그림은 이랬다:

```
실패율 0%          5xx 도 타임아웃도 없음 (커넥션 타임아웃 30초에 한참 못 미침)
앱 CPU 23%         한가함
DB CPU 165%        에러 없이 초당 1.94M 행 처리
Grafana p95 167ms  SLO 200ms 아래 — 초록불 ★
```

**대시보드는 전부 정상이었다. 그런데 사용자는 1.6초를 기다렸다.**

SLO(`p95 < 200ms`)를 서버 지표로만 걸어 두면 **이 장애를 영원히 못 잡는다.**

### 무엇을 봐야 했나

| 신호 | 값 | 보이는 곳 |
| --- | --- | --- |
| `hikaricp_connections_pending` | **189** | Grafana ③ — **차 있었다** |
| `hikaricp_connections_active` | **10 / 10** | Grafana ③ — **천장** |
| `tomcat_threads_busy` | ~190 / 200 | Grafana ⑤ |
| 클라이언트 관점 지연 | **1,627ms** | **k6 만 안다** |

**Saturation 지표는 제대로 경고하고 있었다.** `pending` 189 는 명백한 신호였다.
`docs/02-monitoring.md` 2절의 "Saturation 이 가장 중요한데 가장 자주 빠진다" 가 정확히 이 상황이다.

그리고 **지연은 서버 밖에서 재야 한다.** 실무에서 RUM(Real User Monitoring)이나
로드밸런서 지표를 따로 보는 이유가 이것이다. 이 레포에는 그 층이 없으므로,
당분간은 **k6 의 `http_req_duration` 을 사용자 관점 지연의 유일한 출처로 취급**한다.

### 판정 로직이 작동했다

스모크 테스트 뒤 판정 로직에 구멍을 하나 고쳤다.
`maxVUs` 에 닿았을 때 원인이 두 가지인데 구분하지 못하고 있었다.

```
vus 가 maxVUs 에 닿고 drop 발생
├─ p95 > WORST_RESPONSE  → C: 시스템이 무너져서 VU 가 쌓인 것 (신뢰 가능)
└─ p95 정상              → E: 그냥 VU 설정이 낮았던 것 (설정 실수)
```

본 측정에서 `vus 2250/2250` 으로 천장에 닿았지만 p95(1,627ms)가 예산(500ms)을 넘었으므로
**C 로 올바르게 판정**했다. Grafana 대조(`active` 10.0, `pending` 189)와도 일치한다.

이 구분을 못 하면 **시스템 포화를 "설정 실수" 로 오진**하게 된다.
열린 모델에서 포화의 전형적인 모양이 정확히 "응답이 늘어지며 VU 가 쌓이는 것" 이기 때문이다.

### 시나리오 결함과 수정 (기록)

커서 모드 1차에서 **뒷페이지 비율이 목표 20% 대비 1%** 로 무너졌다.
응답에서 `nextCursor` 를 받아 기억하는 방식이었는데,
본문을 20회에 1번만 파싱하는 데다 VU 2,250개가 각자 커서를 들고 있어서
무작위로 고른 상품의 커서를 갖고 있을 확률이 낮았다.

**커서를 합성하는 방식으로 고쳤다.**

```js
function syntheticCursor() {
  const ts = new Date(Date.now() - Math.random() * 365 * 86400000).toISOString();
  const id = 1 + Math.floor(Math.random() * 100000);
  return encoding.b64encode(`${ts}|${id}`, 'rawurl');   // 앱의 ReviewCursor 와 같은 인코딩
}
```

시드의 `created_at` 이 최근 365일 균등 분포이므로 무작위 시각의 커서는 목록의 임의 위치를 가리킨다.
**서버가 하는 일은 진짜 커서와 완전히 같다.**

부수 효과가 셋이다.
- 응답 파싱이 전혀 필요 없어졌다 (k6 CPU 절약)
- 뒷페이지 비율이 OFFSET 모드와 정확히 같아졌다 (공정한 비교)
- VU 사이 상태 공유가 없어져 재현 가능해졌다

> 이 결함이 결론을 뒤집지는 않았다. 커서가 뒷페이지를 **덜** 때렸다는 건
> OFFSET 이 불리한 조건이었다는 뜻인데, 그래도 OFFSET 처리량이 오히려 약간 높았다.

### 남은 의문: k6 의 CPU

시스템 CPU 81% 중 앱 2.3코어 + DB 1.65코어 + 기타 0.3코어를 빼면 k6 가 약 3.9코어다.
`discardResponseBodies` 를 켰는데도 여전히 크다.

다만 이번에는 **파싱이 아니라 커넥션 관리 비용**으로 보인다 —
2,250개의 VU 가 1.6초짜리 응답을 동시에 붙들고 있었다. 조건이 달라서 v2-3 과 직접 비교할 수 없다.
**정상 상태(포화 아님)에서 다시 재봐야 한다.**

## 6. 결론과 다음 행동

```
부하 모델만 바꿨다 (시스템 무변경)
  → 처리량 천장은 동일:      1,341 → 1,425 RPS
  → 서버 지표 p95 도 거의 동일:  160 → 167 ms
  → 클라이언트 지연은 14배 악화: 119 → 1,627 ms   ★
  → "요구 대비 67.4% 만 처리" 라는 사실이 처음으로 숫자로 나왔다
  → 판정이 추론에서 자동 판정으로 바뀌었다
```

**지금까지의 모든 측정은 처리량은 맞았고, 지연은 "그 부하 모델에서의 값" 이었다.**

그리고 더 중요한 것: **서버 지표 p95 는 두 모델을 구분하지 못했다.**
같은 서버 지표(160 vs 167ms)에 사용자 경험은 119ms 와 1,627ms 였다.
`http_server_requests_seconds` 는 큐 대기를 재지 않기 때문이다.

부수적으로 확인된 것:

- **v2-3(커서)의 결론이 열린 모델에서도 재현됐다.** 행 33배 감소, 처리량 변화 없음.
  닫힌 모델이 뭔가를 가리고 있었던 게 아니다.
- **커서는 뒷페이지 비율에 무감각하다.** 1% → 20% 로 20배 올려도 결과가 같았다.
  깊은 페이지가 첫 페이지와 비용이 같다는 성질이 부하 상태에서도 성립한다.

### 측정 절차 변경

| | 이전 | **이후** |
| --- | --- | --- |
| 주력 시나리오 | `browse.js` (닫힌) | **`browse-arrival.js` (열린)** |
| 단위 | VU + think time | **RPS** |
| think time 환산 | 매번 계산 필요 | **불필요** |
| 천장 판정 | pending/active 로 추론 | **`dropped_iterations` + 자동 판정** |
| **p95 출처** | Prometheus 또는 k6 (혼용) | **둘 다 기록하고 구분해서 쓴다** |

**p95 를 적을 때는 출처를 반드시 명시한다.**

```
서버 p95   (Prometheus http_server_requests) — 앱이 얼마나 빨리 처리했나
클라이언트 p95 (k6 http_req_duration)        — 사용자가 얼마나 기다렸나
```

두 값이 벌어지면 **그 차이가 곧 큐 대기 시간**이다. 이번엔 1,460ms 였다.

`browse.js` / `browse-cursor.js` 는 **지우지 않는다.** v1~v2-3 계보를 재현하려면 필요하다.

### 다음에 바꿀 한 가지: N+1 제거

이제 도구가 준비됐다. 예측은 v2-3 에서 계산해 뒀다.

```
fetch join  →  요청당 쿼리 21개 → 1개 (95% 감소)
예상 DB CPU    165% → 15% 부근
예상 점유 시간  7.0ms → 1ms 부근
예상 천장      1,425 → 10,000 RPS 부근 (10 ÷ 0.001)
```

**측정 설계 주의:**

- `MAX_RATE` 를 예상 천장의 2배인 **20,000** 으로 잡아야 하는데,
  장비 보정값이 **16,000 RPS** 다. 즉 **장비가 먼저 한계일 수 있다.**
- 그 경우 판정 D(도구/장비 한계)가 나온다. 그때는 앱과 부하 도구를 분리하거나,
  천장을 계산으로만 남기고 "장비 한계까지는 확인했다" 로 기록해야 한다.
- **처음으로 "측정할 수 없는 구간" 에 들어갈 가능성이 높다.** 그것 자체를 기록할 것.
