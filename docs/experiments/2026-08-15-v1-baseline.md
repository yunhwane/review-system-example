## 4. 결과

계단식 부하: VU 50 → 100 → 200 → 400 (스크립트 think time 1초)

| 지표 | 값 |
| --- | --- |
| 총 요청 수 | 53,156 |
| 평균 RPS | **136** |
| p50 | 66 ms |
| p95 | **863 ms** |
| 최대 | 1,953 ms |
| 실패율 | 0.00 % |

k6 threshold(`p95 < 200ms`)는 **실패했습니다. 예상대로이고, 그게 이 테스트의 목적입니다.**

### 한계점

VU를 50 → 400으로 8배 올렸지만 RPS는 **136 언저리에서 더 오르지 않았습니다.**
포화된 시스템의 전형적인 모습입니다 — 부하를 더 줘도 처리량은 그대로고 **대기 시간만 늘어납니다.**

### 병목 지점의 지표

| 지표 | 값 | 해석 |
| --- | --- | --- |
| `hikaricp_connections_max` | 10 | 풀 크기 |
| 커넥션 **획득 대기** 평균 | **77 ms** | 요청이 커넥션을 받으려고 기다린 시간 |
| 커넥션 **점유** 평균 | **43~73 ms** | DB 작업에 커넥션을 붙들고 있던 시간 |
| 앱 CPU | 낮음 | **CPU는 놀고 있었다** |
| 시스템 CPU | ~48% (k6 포함) | 여유 있음 |
| 초당 DB 읽은 행 수 | 2,200+ | 20건 주려고 수천 행을 훑음 |

**Little's Law로 검산:**

```
한계 RPS = 커넥션 수 ÷ 커넥션 점유 시간
         = 10 ÷ 0.073s
         = 137 RPS
```

**실측 136 RPS. 계산과 거의 정확히 일치합니다.**
이게 이 실험에서 가장 중요한 결과입니다 — 병목이 커넥션 풀이라는 게 우연이 아니라 **계산으로 설명됩니다.**

### 실행 계획 (EXPLAIN ANALYZE)

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM review WHERE product_id = 1 ORDER BY created_at DESC LIMIT 20;
```

```
Limit (actual time=16.482..16.484 rows=20)
  -> Sort (Sort Method: top-N heapsort  Memory: 56kB)
       -> Seq Scan on review (actual time=0.014..15.337 rows=10028)
            Filter: (product_id = 1)
            Rows Removed by Filter: 89973        ← ★
Execution Time: 16.517 ms
```

**리뷰 20건을 주려고 10만 건을 읽고 89,973건을 버렸습니다.**
여기에 페이징용 count 쿼리(같은 풀스캔, 16.5ms)가 한 번 더 나갑니다.

뒷페이지(OFFSET 9000)는 더 나쁩니다 — 정렬이 메모리를 넘어 **디스크로 넘어갑니다**:

```
Sort Method: external merge  Disk: 2488kB
```

### N+1 확인

리뷰 20건 조회 요청 1회 전후의 Postgres 스캔 카운터:

```sql
SELECT relname, seq_scan, idx_scan FROM pg_stat_user_tables WHERE relname IN ('review','member');
```

| 테이블 | 요청 전 | 요청 후 | 차이 |
| --- | --- | --- | --- |
| `member` idx_scan | 100,004 | 100,024 | **+20** ← 리뷰 1건당 작성자 조회 1번 |
| `review` seq_scan | 9 | 11 | +2 (목록 + count) |
| `review` idx_scan | 0 | 0 | **인덱스를 전혀 쓰지 않음** |

**리뷰 목록 API 한 번에 쿼리가 22번 나갑니다.** (목록 1 + count 1 + 작성자 20)

## 5. 분석

- **실제 병목: HikariCP 커넥션 풀.** 가설이 맞았습니다.
- 다만 예측(250 RPS)보다 실측(136 RPS)이 **낮았습니다.** 이유:
  - 예측할 때 DB 점유 시간을 40ms로 잡았지만, 실제로는 **쿼리 2개(목록+count)에 N+1 20개까지 합쳐 73ms**였습니다
  - **N+1을 계산에 넣지 않은 것이 예측 오차의 원인입니다.** 예측이 틀린 지점이 정확히 배울 지점이었습니다.
- 지표 모양은 `docs/02-monitoring.md` 4절의 첫 번째 줄 그대로였습니다:
  **"앱 CPU 낮음 + DB CPU 낮음 + 커넥션 대기 높음 = 커넥션 풀 고갈"**
- **CPU가 놀고 있는데 느립니다.** 여기서 서버를 늘리거나 사양을 올려도 거의 소용없습니다.
  풀 크기를 늘리거나, 커넥션 점유 시간 자체를 줄여야 합니다.

## 6. 결론과 다음 행동

기준 시나리오(평상시 3,333 RPS)와 비교하면:

```
현재 136 RPS → 목표의 4%
필요 서버 대수로 환산하면 3,333 ÷ 136 ≈ 25대
```

**리뷰 10만 건짜리 서비스에 서버 25대는 명백히 잘못된 설계입니다.**
서버를 늘릴 게 아니라 커넥션 점유 시간을 줄여야 합니다.
