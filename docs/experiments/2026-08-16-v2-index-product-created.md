# 실험: v2-1 — `review (product_id, created_at DESC)` 인덱스 추가

- 날짜: 2026-08-16
- 단계: v2
- 변경 사항: **인덱스 한 개 추가.** 그 외 코드·설정 무변경 (N+1과 OFFSET 페이징은 그대로 둠)

```sql
CREATE INDEX idx_review_product_created ON review (product_id, created_at DESC);
```

> 직전 측정: `2026-08-16-v1-warm-cache-rerun.md` (같은 날, 같은 warm 캐시 조건)

## 1. 가설 (측정 전에 작성)

> 이 절은 인덱스를 만들기 **전에** 작성했습니다. 결과를 보고 고치지 않았습니다.

| 항목 | 예측 | 근거 |
| --- | --- | --- |
| 목록 쿼리 | 23.5ms → **1ms 이하** | Index Scan으로 `product_id=1` 구간에 점프 후 앞 20건만 읽음. 정렬 불필요 |
| count 쿼리 | 16.5ms → **2~3ms** | Index Only Scan. 10,028건을 세지만 좁은 인덱스만 읽음 |
| 뒷페이지(OFFSET 9000) | 15.0ms → **3~5ms** | 디스크 정렬(external merge) 제거 |
| 커넥션 점유 시간 | 34ms → **약 8ms** | 목록+count가 사라지고 N+1 20회 왕복이 지배항으로 남음 |
| 한계 RPS | 294 → **약 1,250** | `10 ÷ 0.008s` |

**그리고 이 사이클의 핵심 예측:**

> **부하 테스트가 새 한계점을 못 찾을 것이다.**
> k6는 VU 400 / think 1초라서 요구 가능한 최대 RPS가 `400 ÷ (1+0.01) ≈ 396`.
> 새 천장(~1,250)의 1/3도 안 된다. RPS는 VU 상한에 걸려 ~395에서 멈추고,
> `pending`은 0, p95는 threshold를 통과할 것이다.
> 즉 "한계를 찾은 것"이 아니라 **"부하가 모자란 것"**이 된다.

병목이 될 것으로 보는 지점: 인덱스로 커넥션 점유 시간이 줄면 **병목이 커넥션 풀에서 벗어난다.**
다음 병목은 N+1의 왕복 횟수, 또는 부하 도구(k6) 자신.

직전 실험과 동일. **인덱스 유무만 다름.**

| DB | Postgres 17 (Docker), `shared_buffers=256MB`, `max_connections=100` |
| 커넥션 풀 | HikariCP **10** (변경 없음) |
| 톰캣 스레드 | 200 (변경 없음) |
| 데이터 | 상품 1,000 / 회원 50,000 / 리뷰 100,001 |
| 부하 도구 | k6 v2.2.0, `load-test/k6/browse.js` (수정 없음), 같은 노트북 |
| DB 캐시 상태 | warm (연속 기동 유지) |
| **인덱스** | **`idx_review_product_created` 추가** ★ |

인덱스 생성 비용: **43ms**, 크기 **3,104 kB** (테이블 60MB의 5%).

> 앱은 재시작하지 않았습니다. `CREATE INDEX`가 relcache 무효화를 보내므로
> 기존 커넥션의 캐시된 실행 계획도 다시 세워집니다.
> `pg_stat_user_tables.seq_scan`이 221,253에서 **전혀 늘지 않는 것**으로 확인했습니다.

## 5. 분석

### 실제 병목의 변화

**병목이 커넥션 풀에서 사라졌습니다.**

```
[v1] active 10 (천장) + pending 148  →  커넥션 풀 고갈
[v2] active 0.3      + pending 0     →  풀은 거의 안 쓰임
```

`docs/02-monitoring.md` 4절 진단표로 보면 v1은 첫 번째 줄(커넥션 풀 고갈)이었고,
v2는 **마지막 줄(부하 도구가 병목)** 로 옮겨갔습니다.
모든 자원이 한가한데 RPS가 VU 상한에 정확히 붙어 있습니다.

### 가설과 다른 점, 왜 달랐나

**① 뒷페이지(OFFSET 9000) 예측이 틀렸습니다. — 이게 가장 배울 게 많은 지점**

인덱스를 만들어놓고도 플래너가 **안 씁니다.** `Parallel Seq Scan + Sort` 그대로입니다.
`enable_seqscan=off`로 강제해서 비교하니 이유가 명확했습니다:

```
Seq Scan 선택   : 15.2ms
인덱스 강제     : 10.5ms  (Bitmap Heap Scan + Sort, temp Disk 3,264kB)
```

인덱스를 써도 10.5ms입니다. 극적인 개선이 없습니다. 이유:

```
OFFSET 9000  →  9,020건이 필요
상품 1의 전체 리뷰 = 10,028건
즉 그 상품 리뷰의 90%를 읽어야 한다
```

**90%를 읽을 거면 순차 읽기가 낫습니다.** 플래너의 판단이 옳았습니다.

> **규칙: 인덱스는 "조금만 읽을 때" 이긴다.**
> 전체의 5~10%를 넘게 읽어야 하면 풀스캔이 이기고, 플래너는 그걸 알고 있다.
> "인덱스를 만들었는데 왜 안 타지?"의 가장 흔한 답이다.

그리고 더 중요한 결론:

> **OFFSET 페이징의 근본 문제는 인덱스로 고칠 수 없다.**
> 커서 페이징(`WHERE created_at < ?`)이면 OFFSET 9000이든 90000이든
> 인덱스로 바로 점프해서 0.2ms에 끝난다. 이것이 v2-3이 따로 있는 이유다.

다만 실전 영향은 작습니다 — k6가 실제로 때리는 뒷페이지는 최대 page 19(OFFSET 380)이고
그건 **0.62ms**로 잘 나옵니다. OFFSET 9000은 극단값 확인용이었습니다.

**② 한계 RPS를 검증하지 못했습니다 (예측대로)**

```
예측 천장     : 10 ÷ 0.0062s = 1,613 RPS
실측 피크     :   399.9 RPS   ← VU 400 ÷ (1초 + 0.007초)
```

**실측값은 시스템의 한계가 아니라 부하 도구의 상한입니다.**
`pending` 0, `active` 0.3, 톰캣 busy 3 — 셋 다 "아직 여유 있다"고 말하고 있습니다.

> **"한계를 넓혔다"가 아니라 "한계가 어디인지 아직 모른다"가 맞는 서술입니다.**
> 이 구분을 못 하면 다음 실험 설계를 틀리게 됩니다.

**③ count가 남은 최대 비용으로 드러났습니다 — 예상 못 한 발견**

v2에서도 요청당 **1,342행**을 훑고 있습니다. 내역:

```
목록 (Index Scan)       :    20 행
member N+1              :    20 행
count (Index Only Scan) : ~1,300 행  ← 여기 ★
```

인기 상품(리뷰 10,028건)은 총 개수를 세려고 인덱스 엔트리 1만 개를 여전히 훑습니다.
**인덱스로 17배 빨라졌지만(16.5ms → 0.97ms) 일의 양 자체는 줄지 않았습니다.**
지프 분포라 인기 상품이 자주 뽑히므로 평균 1,300행이 됩니다.

`count`는 리뷰가 늘수록 선형으로 나빠집니다. 리뷰 100만 건이 되면 여기가 다시 병목입니다.

**④ 시스템 CPU가 87.7% → 28.9%로 떨어졌습니다**

응답이 빨라지면 부하 도구도 편해집니다 (연결을 붙들고 있는 시간이 줄어듦).
**다음 사이클에서 VU를 크게 올릴 여지가 생겼다**는 뜻입니다.

### 이 지표가 그런 모양인 이유

VU 400에서 p95가 오히려 **더 좋아진 것**(37ms → 17ms)이 눈에 띕니다.
포화 시스템이라면 있을 수 없는 모양입니다. JIT 워밍업이 끝났고 커넥션이 이미 열려 있어서,
**부하가 늘수록 단위 요청당 오버헤드가 줄어드는** 구간이었습니다.
포화 전 시스템의 정상적인 모습입니다.

## 6. 결론과 다음 행동

```
인덱스 한 줄 (3MB, 생성 43ms)
  → p95 447.8ms → 31.5ms  (14.2배)
  → DB가 훑는 행 요청당 199,610 → 1,342  (149배)
  → 병목이 커넥션 풀에서 사라짐
```

기준 시나리오(평상시 3,333 RPS) 대비:

```
확인된 처리량 399.9 RPS → 목표의 12%   (단, 이건 부하 도구의 상한이지 시스템 한계가 아님)
계산상 천장   10 ÷ 0.0062s ≈ 1,613 RPS → 목표의 48%, 서버 2.1대
```

베이스라인의 "서버 25대"에서 **인덱스 한 줄로 2대 수준**까지 왔습니다.
다만 **계산값이지 측정값이 아닙니다.** 다음 실험에서 검증해야 합니다.

### 다음에 바꿀 한 가지

**먼저 부하 시나리오를 고쳐야 합니다.** 지금 도구로는 무엇을 바꿔도 399 RPS만 보입니다.

1. **(선행) 부하 상향** — `THINK_TIME=0.2` 또는 VU 계단을 800/1600까지 확장
   → 새 한계점을 실제로 찾는다. 이때 시스템 CPU를 보고 k6가 병목인지 반드시 확인
2. **N+1 제거** (fetch join / `@EntityGraph`) → 요청당 쿼리 22개 → 2개
3. **OFFSET → 커서 페이징** → 뒷페이지 문제 해결 + **`count` 쿼리 제거**

2번과 3번은 **따로 측정**합니다. 예상 개선폭:

| 변경 | 예상 |
| --- | --- |
| N+1 제거 | 점유 6.2ms → 4ms 부근 (왕복 20회가 사라짐) |
| 커서 페이징 | 요청당 훑는 행 1,342 → 40 (count 소멸) |

### 이 실험으로 쓸 ADR

없습니다. 인덱스 추가는 구조 변경이 아닙니다.
다만 다음 두 가지는 **결정으로 기록할 가치가 있습니다** (v2 마무리 시점):

- **커서 페이징 도입** — API 계약이 바뀌므로 ADR 대상 (대안: OFFSET 유지 + count 캐시)
- **부하 시나리오의 think time 기준** — 측정 신뢰도에 직결되므로 문서화 필요
