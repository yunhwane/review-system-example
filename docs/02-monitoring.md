# 모니터링 — 무엇을, 왜 보는가

대시보드에 그래프를 30개 띄우는 건 모니터링이 아닙니다.
**"지금 느린 이유가 무엇인가"에 답할 수 있는 최소한의 지표**를 고르는 게 모니터링 설계입니다.

## 1. 세 가지 층위

| 층위 | 질문 | 이 레포에서 | 
| --- | --- | --- |
| 메트릭 (Metrics) | 얼마나 나쁜가? | Prometheus + Grafana |
| 로그 (Logs) | 무슨 일이 있었나? | 앱 로그, Postgres slow query 로그 |
| 추적 (Traces) | 시간을 어디서 썼나? | (부록) OpenTelemetry + Jaeger |

메트릭은 **문제가 있다는 걸 알려주고**, 추적은 **어디인지 알려주고**, 로그는 **왜인지 알려줍니다.**
셋 다 필요하지만 순서가 있습니다. 메트릭부터 붙이세요.

## 2. RED / USE — 무엇을 볼지 고르는 두 가지 틀

**RED (요청을 받는 서비스에 쓴다)**

| 지표 | 의미 | 이 레포의 Grafana 패널 |
| --- | --- | --- |
| **R**ate | 초당 요청 수 | 처리량 (RPS) |
| **E**rrors | 실패한 요청 비율 | 에러율 (5xx) |
| **D**uration | 응답 시간 분포 | 응답 시간 p50/p95/p99 |

**USE (자원에 쓴다 — CPU, 커넥션 풀, 스레드 풀, 디스크)**

| 지표 | 의미 | 이 레포의 패널 |
| --- | --- | --- |
| **U**tilization | 얼마나 쓰고 있나 | CPU, hikaricp active |
| **S**aturation | 얼마나 밀려 있나 | **hikaricp pending**, 톰캣 busy |
| **E**rrors | 자원 획득 실패 | 커넥션 타임아웃 |

**Saturation(포화)이 가장 중요한데 가장 자주 빠집니다.**
CPU 60%는 정상처럼 보이지만, 커넥션을 기다리는 스레드가 50개 쌓여 있으면 이미 무너진 상태입니다.
이 레포의 v1 병목이 정확히 그 모양입니다.

## 3. 평균을 보지 말 것

응답 시간의 평균은 거의 항상 거짓말을 합니다.

```
요청 100개 중 99개가 10ms, 1개가 5초
평균 = 59.9ms  ← "괜찮네"
p99  = 5,000ms ← 100명 중 1명은 5초를 기다렸다
```

사용자 한 명이 페이지를 열 때 API를 5개 호출한다면, **p99에 걸릴 확률은 1-(0.99)^5 ≈ 5%** 입니다.
즉 p99의 나쁜 경험은 100명 중 1명이 아니라 20명 중 1명이 겪습니다.

그래서 이 레포의 합격 기준은 평균이 아니라 **p95 < 200ms** 입니다.

## 4. 병목별 지표 패턴 (진단 표)

부하를 걸었을 때 아래 중 어느 모양인지 맞춰 보세요. 이 표를 읽을 줄 아는 게 이 단계의 핵심 역량입니다.

| 증상 | 앱 CPU | DB CPU | hikari pending | 톰캣 busy | 진단 |
| --- | --- | --- | --- | --- | --- |
| 느림 | 낮음 (40%) | 낮음 | **높음** | 높음 | **커넥션 풀 고갈** → 풀 크기 or 쿼리 시간 |
| 느림 | 낮음 | **높음 (90%)** | 높음 | 높음 | **쿼리가 무겁다** → 인덱스, N+1 |
| 느림 | **높음 (95%)** | 낮음 | 0 | 높음 | **앱 CPU 한계** → 직렬화/로깅/스케일아웃 |
| 느림 | 낮음 | 낮음 | 0 | **max에 붙음** | **외부 호출 대기** or 스레드 부족 |
| 느림, 톱니 | 튐 | 낮음 | 0 | 높음 | **GC 압박** → 힙, 객체 생성량 |
| RPS가 안 오름 | 낮음 | 낮음 | 0 | 낮음 | **부하 도구(k6)가 병목** ← 자주 놓친다 |

마지막 줄을 꼭 기억하세요. 같은 노트북에서 부하를 주고 있으므로,
**측정 도구 자체가 한계인 경우**가 실제로 자주 발생합니다.

## 5. 부하 테스트 중 확인 절차

```
1. Grafana 를 15분 창으로 열어 둔다
2. k6 를 실행한다
3. VU 가 올라가는 계단마다 아래를 본다:
   - RPS 가 VU 에 비례해서 오르는가?  (안 오르면 그 계단이 한계)
   - p95 가 꺾이는 지점은 언제인가?
   - 그 시점에 hikaricp_connections_pending 이 0 위로 올라왔는가?
   - CPU 는 어떤가?
4. 4번 표에서 해당하는 줄을 찾는다
5. docs/experiments/ 에 기록한다
```

## 6. 알림(Alert)은 언제 붙이나

이 레포에서는 필수가 아니지만, 개념은 알아 둬야 합니다.

- **증상에 알림을 건다. 원인에 걸지 않는다.** "CPU 80%"는 알림이 아니라 정보입니다.
  사용자가 아픈 건 "p95가 500ms를 넘었다"입니다.
- SLO를 먼저 정하고 거기서 알림을 유도합니다. (예: 리뷰 조회 p95 < 200ms를 99% 시간 동안 만족)
- 알림이 너무 많으면 아무도 안 봅니다. 알림 피로는 모니터링이 없는 것보다 나쁩니다.

`application.yml`의 `management.metrics.distribution.slo` 설정이 SLO 버킷을 미리 만들어 두는 부분입니다.

## 7. 직접 해 볼 것

1. `/actuator/prometheus`를 브라우저로 열어 원본 텍스트를 그대로 읽어 보기 — 메트릭이 어떤 형식인지 감을 잡는다
2. Prometheus(localhost:9090)에서 PromQL을 직접 쳐 보기:
   ```promql
   rate(http_server_requests_seconds_count[1m])
   histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket[1m])))
   hikaricp_connections_pending
   ```
3. `rate()`와 `increase()`의 차이, `sum by (le)`가 왜 필요한지 찾아보기
4. Grafana 대시보드에 패널을 하나 직접 추가해 보기 — 예: 초당 DB 쿼리 수
